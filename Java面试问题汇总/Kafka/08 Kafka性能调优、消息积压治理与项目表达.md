# 08 Kafka性能调优、消息积压治理与项目表达

Kafka 性能调优（Performance Tuning）讨论的是端到端吞吐、延迟、资源利用率和故障恢复能力之间的平衡。Kafka 本身擅长顺序写、批量发送、页缓存、零拷贝和分区并行，但业务系统出现消息积压时，根因不一定在 Kafka。生产速度长期大于消费端完整处理速度，才会形成积压；这个“完整处理速度”包括消费者拉取、反序列化、业务计算、数据库写入、外部接口调用、Offset 提交和失败重试。

因此，消息积压治理不能只回答“加消费者”。如果 Topic 只有 4 个分区，启动 20 个同组消费者也只有 4 个能工作；如果瓶颈在 MongoDB 慢写，继续增加消费者只会把下游压垮；如果瓶颈在 Broker 磁盘和网络，消费者扩容也拉不动数据；如果瓶颈来自热点 Key，扩整体并行度可能仍然只有一个分区在排队。比较成熟的排查方式是先用 Lag 定位现象，再沿 Producer、Broker、Consumer、下游四段链路逐段确认瓶颈。

## 一、先用 Lag 判断积压的形态

Consumer Lag 是 Kafka 积压排查的入口。它通常表示某个消费者组在某个 Topic-Partition 上的日志末尾 Offset 与已提交 Offset 之间的差值。Lag 增长，说明写入速度大于消费提交速度；Lag 稳定但不下降，说明消费能力只能勉强追平当前流量，历史积压没有被消化；Lag 持续下降，说明消费者正在追赶历史数据；Lag 突然归零不一定是好事，还要确认是否发生了 Offset 重置、消费者组变化或 Topic 数据过期。

只看总 Lag 容易误判，必须看分区维度。所有分区 Lag 同时升高，通常说明整体消费能力不足、Broker 出现资源瓶颈或下游系统变慢；少数分区 Lag 特别高，通常说明 Key 分布倾斜、单租户流量过大、某类设备集中上报或分区 Leader 所在 Broker 资源异常；Lag 周期性上升又下降，可能是业务峰谷导致的正常缓冲，例如 IoT 设备整点上报、网关断网恢复后补发、批任务集中推送。

排查 Lag 时还要同时看消费速率和提交速率。如果消费者日志显示已经拉取很多消息，但提交 Offset 很慢，瓶颈往往在业务处理或提交策略；如果拉取速率本身很低，可能是消费者并行度不足、Broker 拉取延迟高、网络带宽受限或客户端参数过保守；如果消费者频繁 Rebalance，Lag 会在分区重新分配期间持续堆积，并可能出现重复处理。
| 观察现象 | 可能原因 | 第一优先级动作 |
| --- | --- | --- |
| 全部分区 Lag 持续上升 | 整体消费能力不足或下游变慢 | 看消费者耗时、数据库慢查询、Broker 资源 |
| 单个分区 Lag 异常高 | 热点 Key、单分区 Leader 热点 | 查 Key 分布、租户/设备流量、Leader 分布 |
| Lag 周期性升高后回落 | 正常峰谷或批量上报 | 评估缓冲窗口和告警阈值 |
| Lag 高但消费者 CPU 很低 | 下游 IO 等待、线程阻塞、连接池耗尽 | 查线程栈、连接池、慢接口 |
| Lag 突然归零 | 可能消费完成，也可能 Offset 被重置 | 查消费者组变更和 Offset 操作记录 |

## 二、Producer 段排查：写入是否突然放大或分区不均

Producer 段首先看流量形态。Kafka 积压经常由上游写入突然放大触发，例如设备批量上线、离线网关恢复后补发、定时任务集中上报、日志级别被临时调高、生产者异常重试形成发送风暴。这个阶段要观察发送速率、发送失败率、重试次数、请求延迟、批次大小、本地缓冲等待时间和 buffer.memory 使用情况。

如果生产者本地 RecordAccumulator 长时间堆积，说明消息进入客户端后还没及时发到 Broker。常见原因包括 Broker 响应慢、网络抖动、batch.size 和 linger.ms 组合不合理、压缩 CPU 开销过高、单条消息过大、回调逻辑太重或发送线程被阻塞。异步发送的回调只应该做轻量记录和异常转储，不应该在回调里执行数据库写入、远程接口调用或复杂序列化。

Producer 调优的基本方向是提高批量效率、减少请求次数、控制失败放大。batch.size 决定单个分区批次的目标大小，过小会导致请求过多，过大则可能增加等待和内存占用；linger.ms 允许生产者为了凑批等待一小段时间，日志、指标、设备遥测这类流量通常可以设置几个毫秒换取更高吞吐；compression.type 可以选 lz4、snappy 或 zstd，用 CPU 换网络和磁盘空间；buffer.memory 要能容纳短时间突发，但不能把下游故障掩盖成客户端内存堆积。

可靠性 Topic 不能为了性能随意降低确认级别。关键业务仍应使用 acks=all 和幂等生产者；普通日志或可丢弃指标可以独立 Topic、独立配置，更偏向吞吐。项目里最好按消息重要性分层：设备告警、状态变更、业务事件走可靠配置；调试日志、采样指标、临时埋点可以使用更激进的批量、压缩和保留策略。这样调优不会把所有业务都绑在同一组参数上。

## 三、Broker 段排查：集群资源和分区布局是否支撑当前负载

Broker 段排查要先看资源，再看分布。Kafka 对顺序写友好，但它仍然受磁盘吞吐、Page Cache、网络带宽、请求队列、Controller 状态和副本同步影响。典型指标包括磁盘使用率、磁盘 IO 等待、网络入站/出站流量、请求处理延迟、请求队列长度、Under Replicated Partitions、Offline Partitions、ISR 收缩次数、Leader 分布和分区数量。

如果 Broker 磁盘或网络已经打满，增加消费者通常没有效果，因为生产写入、Follower 复制和消费者拉取都要经过 Broker。此时要考虑扩容 Broker、迁移热点分区、调整副本分布、增加磁盘能力、优化压缩、清理过长保留数据，或者把不同业务 Topic 拆到不同集群。Broker 层的瓶颈表现经常是生产者请求延迟上升、消费者 fetch 延迟上升、ISR 频繁收缩和 Controller 操作变慢。

分区数量决定并行度，但不是越多越好。分区太少会限制消费者组最大并行度，也容易让单分区成为热点；分区太多会增加文件句柄、内存占用、Controller 元数据压力、Leader 选举成本和 Rebalance 成本。创建 Topic 时应按峰值吞吐、单消费者处理能力、顺序性范围和未来扩容空间估算分区数。后期扩分区可以提高并行度，但会改变 Key 到分区的映射，可能破坏“同一 Key 一直落同一分区”的历史顺序假设。

保留策略也会影响性能和补偿能力。保留时间太短，消费者长时间故障后可能无法从 Kafka 回放；保留时间太长，磁盘压力、Segment 数量和恢复成本都会上升。IoT 指标类消息可以按业务查询窗口保留 3 到 7 天，再同步到离线存储；告警、状态变更和关键事件可以保留更久，或进入单独的归档链路。调优时不要只看 Kafka 当前吞吐，还要看故障补偿窗口是否仍然满足业务要求。

## 四、Consumer 段排查：并行度、批量和处理耗时是否匹配

Consumer 段最先看并行度。一个消费者组对某个 Topic 的最大并行度受分区数限制，同一组内一个分区同一时刻只能由一个消费者实例消费。如果 Topic 有 8 个分区，消费者实例或 Spring Kafka concurrency 配到 8 左右才可能充分利用分区；超过分区数的消费者会空闲。若分区数不足，需要评估扩分区是否会影响 Key 顺序，再决定是否扩分区、拆 Topic 或拆业务 Key。

第二看单次拉取和批量处理。max.poll.records 过小会导致拉取频率高、批量落库不充分；过大则可能让单批处理时间超过 max.poll.interval.ms，触发 Rebalance。对于 MongoDB、MySQL、Elasticsearch 等下游，批量写入通常明显优于逐条写入，但批量失败要能定位到具体记录，不能整批无限重试。常见做法是小批量拉取、批量校验、批量写入，部分失败记录拆出进入重试或死信。

第三看业务线程是否被慢操作拖住。消费者线程里如果直接做长时间 CPU 解析、远程接口调用、大对象序列化、复杂聚合或同步写多个数据库，Kafka 拉取能力再强也会被业务处理耗尽。可以将解析、落库、告警推送拆成独立线程池或独立消费者组，通过有界队列、超时、限流和熔断保护主消费线程。对于确实需要顺序的状态流转，应按 Key 串行处理；对于不要求顺序的指标写入，可以在分区内再做批量和异步落库，但 Offset 提交必须与处理结果协调。

IoT 持久化链路里常见的初版实现是“一个 Topic 或一个监听容器直接处理完整业务”，消息量小的时候足够简单，但 Topic 数量和设备上报量增加后，消费线程容易同时承担拉取、解析、分发和落库，最终表现为消息积压、CPU 飙高或 MongoDB 写入排队。优化时可以借鉴多 Reactor、多线程模型的思想：拉取线程负责稳定 poll 和分发，业务线程池负责协议解析和规则判断，落库线程池或批处理组件负责 MongoDB 写入，主消费链路只保留必要的背压、失败转移和 Offset 协调。这里不要求把 Kafka 消费者改造成网络框架式 Reactor，而是要把“事件接收”和“耗时业务处理”拆开，避免慢落库拖死消费进度。

第四看 Rebalance。消费者频繁上线下线、处理时间超过 max.poll.interval.ms、心跳异常、实例扩缩容过于频繁，都会导致 Rebalance。Rebalance 期间分区暂停消费，Lag 会继续增长；如果业务处理和 Offset 提交没有设计好，还可能放大重复消费。生产环境要关注 Rebalance 次数、消费者存活状态、单批处理耗时和提交失败率，必要时调整 session.timeout.ms、heartbeat.interval.ms、max.poll.interval.ms，并使用静态成员或更稳定的部署方式降低抖动。

## 五、下游段排查：很多积压根因不在 Kafka

Kafka 只是缓冲和传输层，最终处理能力经常由下游系统决定。消费者每条消息单独写 MongoDB、MySQL 或 ES 时，吞吐往往远低于 Kafka 拉取能力；下游索引不合理、连接池不足、慢查询、锁冲突、批量大小不合适、磁盘写入慢、接口限流，都可能表现为 Kafka Lag 增长。此时继续增加消费者会让下游排队更严重，甚至把局部慢写扩大成系统故障。

下游治理要先区分写入模型。设备遥测数据通常适合批量写入、按时间分区或分集合、建立 deviceId + eventTime 等查询索引；告警状态适合幂等 upsert 和状态机更新；统计大屏适合从 Kafka 派生一个专用消费者组，把实时聚合结果写入 Redis 或时序库；审计日志适合异步归档。不同模型不要共用同一个消费者逻辑，否则一个慢场景会拖住整个消费组。

下游不可用时要有削峰和保护。短暂故障可以让消息在 Kafka 中缓冲，但要监控剩余保留时间和 Lag 增速；故障持续时，应对非关键消费降级、暂停某些分区、降低生产速率或启用限流，避免把数据库压垮。关键链路可以用重试 Topic 和死信 Topic 隔离异常消息，主链路只处理健康数据，失败数据由补偿任务按节奏回放。

## 六、顺序、吞吐和热点之间没有免费解

Kafka 单分区内有序，跨分区不保证全局顺序。为了保证同一订单、同一设备或同一工单的事件顺序，通常会用业务 Key 分区，让相同 Key 的消息进入同一分区。同一分区只能被同一消费者组里的一个消费者实例处理，因此 Key 级顺序和无限并行天然冲突。

热点 Key 是顺序性带来的常见副作用。一个大型租户、一个高频设备、一条生产线或一个超级订单如果持续产生大量消息，而分区策略又让它们固定落在同一分区，这个分区就会成为积压点。解决方式不是简单把 Key 去掉，因为去掉 Key 可能破坏顺序；更合理的做法是重新定义顺序边界：设备指标可以按 deviceId + metricType 拆 Key，告警和状态变更仍按 deviceId 保序；租户消息可以按租户下的设备或业务子域拆分；日志类消息可以不保序，使用粘性分区或轮询提高均衡性。

扩分区也要谨慎。Kafka 默认分区计算依赖 Key 的哈希对分区数取模，分区数变化后，同一个 Key 未来可能落到新分区，历史消息仍在旧分区，跨新旧分区的严格顺序就不再天然成立。因此，强顺序 Topic 在扩分区前要评估是否存在未消费历史消息，是否能接受顺序边界从“全历史”变成“扩容之后”，或者是否需要新建 Topic 并按新分区策略迁移。
| 目标 | 常用策略 | 代价 |
| --- | --- | --- |
| 提高吞吐 | 增加分区、批量发送、批量消费、压缩 | 资源和运维复杂度上升 |
| 保证 Key 顺序 | 相同 Key 固定分区 | 热点 Key 会限制并行度 |
| 降低热点 | 拆 Key、拆 Topic、拆业务域 | 需要重新定义顺序范围 |
| 降低延迟 | 减小批量等待、优化下游写入 | 吞吐和压缩率可能下降 |

## 七、重试队列和死信队列要服务主链路稳定

失败处理不能只依赖消费者日志。生产系统通常会设计主 Topic、重试 Topic 和死信 Topic，让临时失败有节奏地重试，让永久失败从主消费链路剥离。这样既能保证健康消息继续处理，也能保留异常消息用于补偿和人工排查。

重试 Topic 适合可恢复错误，例如数据库短暂不可用、网络超时、下游限流、锁冲突和临时依赖故障。重试应该有次数上限和退避策略，可以按 retry\_5s、retry\_1m、retry\_10m 分层，也可以使用延迟队列组件实现。每次重试都应携带原始 Topic、Partition、Offset、Key、失败原因和重试次数，避免一条坏消息在主链路里无限阻塞。

死信 Topic 适合不可恢复或超过重试上限的消息，例如 JSON 格式错误、必填字段缺失、协议版本不兼容、业务状态永远不合法。死信不是“丢弃”，而是把异常消息变成可观测、可检索、可补偿的数据资产。后台可以按错误类型聚合死信数量，提供人工修正、重新投递、跳过确认和告警通知能力。

## 八、监控要能反推瓶颈位置

Kafka 监控不能只看一个 Lag。Producer、Broker、Consumer 和下游都要有指标，并且指标之间要能互相解释。Producer 关注发送速率、失败率、重试次数、请求延迟、批次大小、压缩率、缓冲等待时间；Broker 关注磁盘、网络、请求队列、ISR、Under Replicated Partitions、Offline Partitions、Controller、Leader 分布；Consumer 关注 Lag、拉取速率、处理耗时、提交失败率、Rebalance 次数、poll 间隔；业务侧关注落库成功率、慢查询、接口超时率、连接池等待、死信数量和端到端延迟。

更重要的是用指标定位问题。Lag 上升、Broker 指标正常、消费者 CPU 很低、数据库慢查询上升，瓶颈大概率在下游数据库；Lag 上升且只有一个分区特别高，要看 Key 倾斜和热点设备；Producer 请求延迟上升、ISR 收缩、Under Replicated Partitions 增加，说明 Broker 或副本同步异常；消费者 Rebalance 次数增加且单批处理耗时接近 max.poll.interval.ms，说明消费逻辑过慢或部署不稳定。

告警阈值也要结合业务窗口。IoT 实时告警链路可能要求秒级到分钟级处理，Lag 超过几万就要告警；离线指标归档可以允许更大的缓冲，但要监控“按当前消费速度多久能追平”和“Kafka 保留时间还剩多少”。只配置固定 Lag 阈值不够，最好同时配置 Lag 增速、端到端延迟、死信增长率和下游错误率。

## 九、IoT 项目中的表达方式

在工业智能工厂 IoT 项目中，可以把 Kafka 设计讲成一条实时数据管道：设备网关将遥测数据、状态变更和告警事件写入 Kafka，不同类型消息拆成不同 Topic；关键状态和告警使用设备 ID 作为 Key，保证同一设备关键事件在分区内有序；消费者组按业务职责拆分，例如实时告警、MongoDB 持久化、大屏统计和离线归档互不影响；关键 Topic 使用三副本、可靠生产者配置和手动提交 Offset，消费成功后再推进位移。

如果被追问“为什么会消息积压”，可以从四段链路回答：上游可能因为设备批量上线、网络恢复补发、定时任务集中上报导致流量突增；Broker 可能因为磁盘、网络、ISR 收缩或分区 Leader 不均衡导致吞吐下降；消费者可能因为分区数不足、实例数不足、批量配置不合理、Rebalance 频繁或单条处理过慢导致追不上；下游 MongoDB 可能因为逐条写入、索引缺失、连接池不足或慢查询成为真正瓶颈。

如果被追问“你们怎么优化”，可以落到具体方案：先通过 Consumer Lag 和分区维度定位是整体慢还是局部热点；整体慢时增加消费者并发到不超过分区数，同时把逐条落库改成批量写入；热点分区时分析设备 ID 或租户流量，必要时拆分 Topic 或重新设计 Key；MongoDB 慢时优化索引、批量大小、连接池和写入模型；异常消息阻塞时进入重试和死信 Topic；上游突发时配合限流、削峰和告警保护下游。这样的表达既说明 Kafka 原理，也能体现项目排障能力。

项目复盘时还可以补一句取舍：Kafka 不是越快越好，而是要让可靠性、顺序性、实时性和下游承载能力匹配。设备指标可以更偏吞吐，允许批量和压缩；设备告警更偏实时和可靠，要求快速处理、幂等落库和失败告警；状态变更更重视同一设备顺序，不能为了并行度随意打散 Key。能讲出这种分层，面试官会更容易相信你真的做过设计。

## 十、本章准备标准

这一章要准备到能用一张排查表解释 Kafka 积压：先看 Lag 的分区分布，再沿 Producer、Broker、Consumer、下游四段定位瓶颈。Producer 侧要能讲批量、压缩、缓冲、重试和可靠性取舍；Broker 侧要能讲磁盘、网络、ISR、Leader 分布、分区数量和保留策略；Consumer 侧要能讲分区并行度、max.poll.records、批量落库、Rebalance 和处理耗时；业务侧要能讲热点 Key、顺序边界、重试死信、监控指标和 IoT 项目表达。遇到“消息积压怎么办”这类题，先定位瓶颈，再选择扩容、调参、拆分、限流或补偿，而不是直接回答“加机器”。
