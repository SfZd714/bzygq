09 链路追踪、可观测与线上故障排查 ​

可观测性（Observability）是微服务系统上线后用于回答“系统现在发生了什么、为什么发生、影响范围有多大”的工程能力。它不是某一个监控大盘，也不是单独接入一个链路追踪工具，而是一套由日志、指标、链路追踪、告警和故障动作组成的闭环体系。Spring Cloud 项目拆分成多个服务之后，一次请求可能经过 Gateway、用户服务、设备服务、告警服务、Redis、数据库、MQ 和第三方接口，单看某个应用日志很难判断慢点和错误点，因此必须让请求在跨服务、跨线程、跨消息的过程中保留同一个诊断上下文。

从面试和项目表达角度看，这一章要掌握四条主线：第一，日志、指标、链路追踪分别解决什么问题；第二，traceId、span、MDC 怎样把一次请求串起来；第三，Micrometer Tracing、OpenTelemetry、SkyWalking、Prometheus、Grafana 这些工具的边界是什么；第四，线上慢接口和偶发失败如何按模板排查。能把这四条讲清楚，就不会只停留在“我们用了 SkyWalking”或“日志里打印 traceId”这种表层回答。

一、可观测三件套的定位 ​

日志、指标和链路追踪是可观测系统的三类核心信号。日志记录离散事件，例如某个请求进入网关、某个 Feign 调用返回 500、某次 SQL 执行异常、某条 MQ 消息消费失败。日志的优势是细节丰富，适合还原某一次请求或某个异常现场；缺点是数量大、检索成本高，如果没有 traceId、服务名、实例、接口和业务键，很容易变成一堆无法关联的文本。

指标记录聚合状态，例如 QPS、错误率、P95/P99 延迟、CPU、内存、线程池队列长度、连接池活跃数、数据库慢 SQL 数、MQ 堆积量。指标的优势是能发现趋势和范围，适合做大盘、告警和容量判断；缺点是它通常不能直接告诉你某一次请求为什么失败，只能告诉你“哪个维度不正常”。

链路追踪记录一次请求跨组件的调用路径。一个 trace 表示完整请求链路，一个 span 表示链路中的一个片段，例如 Gateway 转发、用户服务 Controller、Feign 调用设备服务、设备服务查询数据库、发送 MQ 消息等。链路追踪的优势是能定位慢点和错误传播路径；缺点是它不替代日志和指标，span 上的标签也不应该无限堆业务字段。

images/09-observability-signal-correlation.png

这三类信号要一起使用。指标先告诉我们“系统异常了”，链路追踪告诉我们“异常集中在哪一段调用”，日志再解释“这一段为什么失败”。如果只看日志，值班人员可能被海量文本淹没；如果只看指标，知道 P99 升高却不知道慢在哪里；如果只看链路，能看到某个 span 慢，却不一定知道线程池、连接池、GC、数据库锁等待是否是根因。

信号主要回答的问题常见字段或指标适合的动作
日志某次请求发生了什么traceId、spanId、接口、用户、租户、错误摘要定位异常原因、还原现场
指标系统整体是否异常QPS、错误率、P99、CPU、线程池、连接池发现趋势、触发告警、判断影响范围
链路请求卡在哪个调用段trace、span、parentSpan、duration、tag找慢点、找跨服务错误传播

二、traceId、span 与 MDC 的协作机制 ​

traceId 用来标识一次完整请求，span 用来标识请求中的一个工作片段。一个外部请求进入 Gateway 时，如果上游没有传入合法追踪上下文，网关或追踪框架会生成新的 traceId；随后每经过一个服务、一次远程调用、一次数据库访问或一次消息消费，都会创建新的 span，并通过 parent span 关系形成调用树。这样在链路平台中就能看到请求从入口到下游依赖的完整路径。

span 的价值不只是“画出树”。一个 span 通常会记录开始时间、结束时间、耗时、状态、服务名、接口名、异常信息和少量标签。比如 Feign 调用 device-service 耗时 1800ms，span 上可以标记目标服务、HTTP 方法、路径、状态码和异常类型。排查时如果发现整个请求耗时 2200ms，而某个下游 span 占了 1800ms，就可以先把注意力集中到这个下游，而不是盲目翻所有服务日志。

MDC（Mapped Diagnostic Context）是日志框架中的线程上下文容器，常见于 Logback、Log4j2 等实现。追踪框架会把当前 traceId、spanId 写入 MDC，日志 pattern 再把这些字段打印出来。例如日志格式中包含 %X{traceId}、%X{spanId}，同一条调用链上的网关日志、应用日志、异常日志就能通过 traceId 检索到一起。MDC 的边界也要清楚：它通常依赖当前线程上下文，线程切换、线程池复用、异步任务和 MQ 消费都会带来上下文丢失风险。

工程里常见的日志字段可以固定成一套规范：traceId 用于跨服务串联，spanId 用于定位当前片段，service 表示服务名，instance 表示实例，env 表示环境，uri 表示接口路径，cost 表示耗时，status 表示结果，bizId 表示订单号、设备号、任务号等业务定位键。敏感字段不能为了排查方便随意写入日志，Token、密码、手机号、身份证、密钥要脱敏或禁止打印。

面试中可以这样表达：traceId 解决跨服务日志关联问题，span 解决调用片段和父子关系问题，MDC 解决日志打印当前追踪上下文的问题。三者组合后，指标发现异常，trace 定位慢 span，日志用同一个 traceId 还原具体异常，这才是完整的排查链路。

三、上下文在 HTTP、Feign、线程池和 MQ 中传播 ​

追踪上下文必须跟着请求流动。HTTP 场景中，追踪上下文通常通过请求头传递，常见标准是 W3C Trace Context 中的 traceparent 和 tracestate，也可能兼容 B3 Header。外部请求进入 Gateway 后，网关会解析或生成上下文；转发到下游服务时，把上下文写入请求头；下游收到请求后恢复上下文，并创建新的服务端 span。只要每一跳都遵守同一套传播协议，完整链路就能连起来。

OpenFeign 本质上还是 HTTP 客户端封装，因此上下文传播依赖拦截器和追踪框架集成。调用方发起 Feign 请求时，需要把当前 trace 上下文注入到下游请求头；被调用方通过 Servlet Filter、WebFlux Filter 或框架自动配置提取上下文。项目中如果出现“入口有 traceId，下游日志没有 traceId”，要重点检查 Feign 拦截器是否生效、追踪依赖是否完整、服务之间是否经过了丢失 Header 的代理、日志 pattern 是否打印 MDC 字段。

线程池是 traceId 丢失的高频位置。MDC 默认绑定当前线程，而线程池会复用工作线程；如果提交任务时没有把上下文复制过去，异步任务里的日志就可能没有 traceId，甚至打印出上一批任务残留的 MDC。解决方式通常是使用框架提供的上下文传播能力，例如 Micrometer Context Propagation、TaskDecorator、TTL 类库、Reactor Context 或追踪框架适配的 Executor 包装器。写自定义线程池时，要把“任务提交时捕获上下文、执行前恢复上下文、执行后清理上下文”作为固定动作。

MQ 会把同步调用链切成异步链路。生产者发送消息时，应把 traceId 或标准 trace header 写入消息 Header；消费者收到消息后，从 Header 恢复上下文并创建消费 span。这样一次用户请求触发 MQ 后，后续消费、重试、死信和补偿日志仍然可以关联到原始请求。IoT 设备上报、告警通知、任务派发、报表生成这类链路尤其需要注意 MQ 传播，否则排查时只能看到“生产成功”和“消费异常”两堆孤立日志。

images/09-trace-context-propagation.png

跨上下文传播的排查可以按四层看：入口层确认网关是否生成 trace；同步调用层确认 HTTP/Feign Header 是否透传；异步执行层确认线程池和 Reactor 是否传播上下文；消息层确认生产者 Header、消费者恢复和重试链路是否保留 trace。很多项目的链路断点不在追踪平台，而在这些边界没有被统一包装。

四、Micrometer Tracing、OpenTelemetry、SkyWalking、Prometheus 与 Grafana 的边界 ​

Spring Boot 3 之后，原来常见的 Spring Cloud Sleuth 逐渐让位给 Micrometer Observation、Micrometer Tracing 和 OpenTelemetry 体系。Micrometer Observation 更像统一观测 API，负责把一次操作抽象成可观测事件；Micrometer Tracing 负责把追踪能力接入 Spring 生态，并可以桥接 Brave 或 OpenTelemetry；OpenTelemetry 则是更通用的观测标准，定义 trace、metric、log 的 API、SDK 和协议，适合跨语言、跨框架统一采集。

SkyWalking 更偏向一体化 APM 平台。它通常通过 Java Agent 或 SDK 采集服务调用、数据库访问、HTTP 客户端、MQ 等链路数据，并提供拓扑图、调用链、实例指标、慢端点分析等能力。它的优势是开箱体验好，适合 Java 微服务项目快速获得链路视图；边界是不要把所有监控需求都塞给 SkyWalking，业务指标、基础设施指标、日志检索和告警治理仍然需要配合其他系统。

Prometheus 主要负责指标采集和存储。Spring Boot Actuator 与 Micrometer Metrics 可以暴露 /actuator/prometheus，Prometheus 按 scrape 模型定期拉取指标。它适合存储时间序列指标，例如请求耗时直方图、JVM、线程池、连接池、数据库连接、MQ 消费延迟、Sentinel 规则触发次数等。Prometheus 不适合保存大量明细日志，也不是链路追踪数据库。

Grafana 主要负责可视化和告警编排。它从 Prometheus、Loki、Tempo、Elasticsearch、ClickHouse 等数据源查询数据并展示大盘，也可以配置告警规则。Grafana 的价值在于把入口、服务、JVM、数据库、MQ、业务指标放在同一套视图里，让值班人员快速判断影响范围。它不是数据采集器本身，也不自动理解业务链路。

工具或体系更适合承担的职责不适合替代的职责
Micrometer TracingSpring 生态内追踪接入、traceId/span 生成与传播独立 APM 平台、日志存储

面试时不要把工具名罗列成清单。更好的说法是：“在 Spring Boot 3 项目里，我会优先用 Micrometer 体系接入观测；如果要跨语言和标准协议，采用 OpenTelemetry；链路分析可以落到 SkyWalking、Tempo、Jaeger 等后端；指标通过 Micrometer 暴露给 Prometheus；Grafana 负责大盘和告警展示。工具可以替换，但日志、指标、链路三类信号和上下文传播机制不能缺。”

五、SLI、SLO 与告警动作 ​

SLI（Service Level Indicator）是服务水平指标，描述系统实际表现；SLO（Service Level Objective）是服务水平目标，描述系统希望达到的质量线。微服务项目里常见 SLI 包括请求成功率、P95/P99 延迟、错误率、可用性、饱和度、MQ 消费延迟、数据处理成功率。SLO 则把它们变成明确目标，例如“核心查询接口 99% 请求在 300ms 内返回”“设备上报链路 5 分钟内消费延迟不超过 30 秒”“核心下单接口月可用性达到 99.9%”。

告警应该围绕 SLO 设计，而不是围绕单个异常日志设计。单次 500 不一定需要半夜叫醒值班人员，但核心接口错误率连续 5 分钟超过 1%、P99 连续 10 分钟超过 SLO、线程池队列持续打满、数据库连接池耗尽、MQ 堆积持续增长、核心租户成功率明显下降，就应该触发告警。告警要能触发动作，否则只是噪声。

一个合格告警至少包含服务名、接口或资源名、环境、实例、当前值、阈值、持续时间、影响范围、最近变更和样例 traceId。比如“device-service 的 /devices/{id}/status P99 在 10 分钟内从 180ms 升到 2100ms，错误率 0.2%，主要影响华东生产环境，样例 traceId 为 xxx，最近 30 分钟有配置变更”。这样的告警能直接引导值班人员进入排查，而不是只看到“接口慢”三个字。

告警也要分级。P0 通常对应核心链路不可用、大面积 5xx、数据库不可写、MQ 长时间堆积、网关入口异常；P1 对应核心接口明显劣化但仍可用、单区域或单租户影响、重要异步任务积压；P2 对应非核心接口波动、少量实例异常、容量逼近阈值。分级的目的不是形式化，而是决定响应速度、通知范围和故障动作。

故障动作可以分成观察、止血、定位、修复和复盘。观察阶段看大盘和影响范围；止血阶段可以限流、熔断、降级、回滚配置、摘除异常实例、暂停低优先级任务；定位阶段结合 trace、日志、指标查根因；修复阶段处理代码、配置、容量或依赖问题；复盘阶段补充告警、仪表盘、压测用例和应急预案。可观测性的终点不是“看见问题”，而是让团队更快做出正确动作。

六、慢接口排查模板 ​

images/09-incident-diagnosis-loop.png

慢接口排查的第一步是确认“慢”的定义。不要只凭用户反馈说慢，要看入口层和服务层的 P95、P99、平均耗时、最大耗时、请求量和错误率。平均耗时容易掩盖尾部延迟，P99 更能反映真实体验；同时要看 QPS 是否突增，因为流量变化会影响线程池、连接池、缓存命中和数据库负载。

第二步是判断慢点所在层级。入口层看 Gateway、Nginx、负载均衡和鉴权过滤器；服务层看 Controller、业务方法、Feign 调用、线程池和序列化；存储层看数据库慢 SQL、索引、锁等待、连接池、Redis 命中率；异步层看 MQ 堆积、消费耗时和重试；外部依赖看第三方接口、网络和超时。链路追踪的慢 span 可以把排查范围从“整个系统”缩小到“某个调用段”。

第三步是结合资源指标验证根因。慢 span 在数据库查询上，不代表一定是 SQL 问题，还要看连接池是否耗尽、是否有锁等待、是否发生全表扫描、是否被其他任务抢占资源。慢 span 在 Feign 调用上，也要看下游服务 P99、调用方连接池、超时设置、重试次数、熔断状态和目标实例分布。慢 span 在业务方法内部，则要看 CPU、GC、线程栈、锁竞争、大对象序列化和本地缓存。

第四步是先止血再深入。若是突发流量导致队列堆积，可以按租户、用户、设备、接口维度限流；若是下游慢导致上游线程堆积，可以收紧超时、开启熔断降级或临时关闭非核心功能；若是配置变更导致慢，可以回滚配置；若是单实例异常，可以摘除实例并保留现场；若是 SQL 退化，可以临时加索引、降级查询条件或切走高风险功能。止血动作要记录时间点，方便与指标变化对齐。

慢接口的口述模板可以这样组织：“我会先用指标确认慢接口的 P95/P99、QPS 和影响范围，再通过 traceId 找到耗时最长的 span，判断慢在网关、服务、数据库、缓存、MQ 还是第三方依赖。随后结合具体资源指标验证根因，例如线程池、连接池、GC、慢 SQL、锁等待和下游 P99。处理上先做止血，例如限流、熔断、降级、回滚配置或摘除实例，最后再修复代码、SQL、容量或依赖问题。”

七、偶发失败排查模板 ​

images/09-async-context-loss-points.png

偶发失败比持续失败更考验观测体系，因为它可能只影响少量请求、少量实例、特定租户或特定时间窗口。排查时先把失败分类：连接超时、读取超时、HTTP 4xx、HTTP 5xx、业务错误码、序列化失败、连接池耗尽、熔断拒绝、限流拒绝、MQ 消费失败、数据库死锁、配置不一致。分类越清楚，排查路径越短。

连接超时通常说明请求没有在规定时间内建立连接，可能是目标实例不可达、端口未监听、网络抖动、连接池配置异常、注册列表有脏实例。读取超时通常说明连接建立了，但下游响应太慢，常见原因是下游线程池阻塞、数据库慢、外部依赖慢、GC 停顿或服务过载。4xx 更多与参数、鉴权、路由、灰度、版本兼容有关；5xx 更多与下游异常、空指针、资源耗尽或依赖失败有关。

偶发失败要特别关注“只发生在某些实例上”的情况。微服务扩容后，某个新实例配置缺失、版本不一致、权限不足、DNS 异常、证书过期、连接池参数不同，都可能导致部分请求失败。此时指标要按 service + instance + uri + status 维度下钻，链路要看失败请求是否集中到某个实例，日志要对比正常实例和异常实例的启动参数、配置版本和依赖状态。

重试也会放大偶发失败。一次下游短暂抖动，如果调用方配置了多次重试，可能在上游表现为延迟升高和流量放大；如果写接口没有幂等，重试还可能造成重复下单、重复扣减或重复通知。排查偶发失败时要看重试次数、退避策略、调用方超时和下游实际处理时间，避免“调用方已经超时重试，下游还在继续执行”的半成功状态。

偶发失败的口述模板可以这样组织：“我会先按错误类型分类，再按服务、实例、接口、租户和时间窗口聚合，确认是否集中在某些实例或某类请求。同步调用看连接超时、读取超时、状态码、下游 P99、连接池和重试；异步链路看 MQ Header 中的 trace、消费失败原因、重试次数和死信；如果是灰度或配置变更后出现，就优先核对版本、配置和路由规则。处理上先降低影响面，再保留样例 traceId 和日志做根因分析。”

八、项目落地与面试表达 ​

项目里落地可观测系统，第一步不是选平台，而是统一规范。日志规范要明确字段、脱敏、采样和保留周期；指标规范要明确服务指标、JVM 指标、依赖指标、业务指标和标签维度；链路规范要明确 HTTP、Feign、线程池、Reactor、MQ 的上下文传播；告警规范要明确 SLO、阈值、持续时间、分级和处理人。没有这些规范，工具接得再多也会变成割裂的数据孤岛。

第二步是把观测埋点放到关键边界。入口层记录请求量、状态码、耗时、限流、鉴权失败和路由目标；服务层记录 Controller、核心 Service、Feign 调用、线程池、连接池、异常和业务关键状态；存储层记录慢 SQL、连接池、Redis 命中率和缓存击穿风险；消息层记录生产、消费、重试、死信和消费延迟；第三方依赖记录超时、错误码、重试和熔断状态。可观测不是只看应用内部，也要看依赖和边界。

第三步是控制成本和噪声。日志不能无限打印，链路不能所有请求都全量采样，指标标签不能无限高基数。用户 ID、订单号、设备号这类高基数字段如果直接作为指标标签，会让时间序列爆炸；大请求体、响应体、Token 和隐私字段如果写入日志，会带来成本和安全风险。工程里通常会对普通请求采样，对错误请求和慢请求提高采样率，对敏感字段做脱敏，对高基数字段放日志而不是指标标签。

面试中可以用下面这段表达可观测落地：“我们项目不是只接入一个链路追踪平台，而是把日志、指标、链路和告警做成闭环。请求进入 Gateway 时生成或接收 traceId，经过 Feign、线程池和 MQ 时继续传播；日志通过 MDC 打印 traceId 和 spanId；指标通过 Micrometer 暴露给 Prometheus，Grafana 展示入口、服务、JVM、数据库和 MQ 大盘；链路平台用于查看调用树和慢 span；告警围绕 SLI/SLO 配置，触发后按影响范围先止血，再结合 trace 和日志定位根因。”

如果面试官追问工具边界，可以继续补充：“Micrometer Tracing 更偏 Spring 生态内的追踪接入，OpenTelemetry 是跨语言标准，SkyWalking 是 APM 分析平台，Prometheus 存时间序列指标，Grafana 做可视化和告警视图。它们解决的问题不同，不能互相完全替代。真正重要的是上下文传播、指标口径、日志规范和故障动作，而不是背某个工具名。”

九、学习自测 ​

1. 日志、指标和链路追踪分别解决什么问题？ 参考回答：日志解释单次事件和异常细节，指标反映系统趋势和聚合状态，链路追踪展示一次请求跨服务的调用路径。排查时通常先看指标确认异常范围，再看链路定位慢点或错误传播，最后用日志还原具体原因。

2. traceId、spanId 和 MDC 的关系是什么？ 参考回答：traceId 标识完整请求链路，spanId 标识当前调用片段，MDC 负责把当前线程里的 traceId、spanId 放进日志上下文。日志 pattern 打印 MDC 字段后，同一条链路上的日志就可以被串起来。

3. 为什么异步线程和 MQ 场景容易丢 traceId？ 参考回答：MDC 和追踪上下文通常绑定当前执行上下文，线程池复用、异步任务切换和消息投递都会打断原来的调用栈。线程池需要上下文包装，MQ 需要生产者写 Header、消费者恢复上下文并创建新的消费 span。

4. Prometheus 和 SkyWalking 的边界怎样区分？ 参考回答：Prometheus 主要采集和查询时间序列指标，适合 QPS、延迟、错误率、JVM、线程池、连接池等指标；SkyWalking 更偏 APM，适合看调用链、服务拓扑、慢端点和跨服务依赖。Prometheus 不能替代调用树，SkyWalking 也不应该承担全部日志和业务指标治理。

5. 线上接口突然变慢，排查顺序是什么？ 参考回答：先看 QPS、错误率、P95/P99 和影响范围；再用 trace 找耗时最长的 span；随后检查慢点对应的线程池、连接池、GC、慢 SQL、缓存、MQ 或第三方依赖；处理上先限流、熔断、降级、回滚配置或摘除异常实例，再做代码、SQL、容量和依赖修复。

6. 偶发失败为什么要按实例维度下钻？ 参考回答：偶发失败常常来自少量实例版本不一致、配置缺失、证书或权限异常、注册脏实例、连接池参数不同等问题。按服务整体看错误率可能不高，但按实例、接口、租户、状态码维度下钻，就能发现失败是否集中在某个节点或某类请求上。

7. 告警信息里为什么最好带样例 traceId？ 参考回答：样例 traceId 能把告警从聚合指标直接连接到具体请求链路和值班日志检索。值班人员拿到 traceId 后可以快速查看调用树、慢 span、异常日志和相关业务键，减少从大盘到现场的跳转成本。

8. 面试中如何一句话总结可观测体系？ 参考回答：可观测体系通过指标发现异常，通过链路追踪定位跨服务慢点和错误传播，通过带 traceId 的日志还原具体原因，再通过 SLI/SLO 告警和止血动作形成线上故障处理闭环。
