MQTT 订阅选项、共享订阅与 Topic 治理 ​

前面几篇已经讲过 MQTT 的发布订阅模型、Topic 路由、QoS、Retained Message 和 MQTT 5 的增强能力。这一篇继续往深处走：在真实 Java 后端和物联网项目里，Topic 不是随手拼出来的字符串，订阅也不是只写一个 client.subscribe("xxx/#") 就结束。Topic 命名空间决定 Broker 如何匹配消息，决定 ACL 能不能写清楚，决定日志、指标、告警能不能按租户、产品、设备、事件类型聚合；MQTT 5 的订阅选项则决定同一条匹配消息是否回到发布者连接、retain 标志如何转发、新订阅建立时是否补发 retained 消息；共享订阅进一步让多个 Session 可以分担同一个 Topic Filter 命中的消息。

images/mqtt-09-subscription-options-shared-routing.png

一、Topic 命名空间是路由、权限与观测的共同底座 ​

Topic Name 与 Topic Filter 的边界 ​

MQTT 规范把 Topic Name 和 Topic Filter 分得很清楚。Topic Name 是发布端放在 PUBLISH 报文里的主题名称，表示这条应用消息归属哪一个具体路由；Topic Filter 是订阅端放在 SUBSCRIBE 报文里的过滤条件，表示当前 Session 想接收哪些 Topic Name 上的消息。Broker 收到发布消息后，用 Topic Name 去匹配已经登记的 Topic Filter，然后再结合会话状态、最大 QoS、保留消息、共享订阅等规则完成投递。

这个边界在面试和项目排障里非常重要。发布端不能向 tenant/+/device/+/status 这种带通配符的字符串发布消息，因为 + 和 # 只能出现在 Topic Filter 中，不能出现在 Topic Name 中。订阅端可以订阅 tenant/+/device/+/status，让 Broker 帮它匹配多个具体设备的状态 Topic。换句话说，Topic Name 是一条消息的精确地址，Topic Filter 是一类消息的匹配模式。

官方规范还规定，Topic Name 和 Topic Filter 都是 UTF-8 编码字符串，至少一个字符，编码后不能超过 65535 字节；二者区分大小写，可以包含空格，但不能包含 Unicode 空字符 U+0000。Broker 做订阅匹配时不能擅自做大小写归一化、Unicode 替换或路径规范化，每个非通配层级都要逐字符匹配。因此 Device/001/status 和 device/001/status 是两个不同 Topic，tenant/t1/device/d1 与 tenant/t1/device//d1 也不是同一个命名。

命名空间要先服务治理，再服务编码方便 ​

很多物联网项目一开始把 Topic 当成字符串常量，后来才发现权限、审计、流量分析和灰度发布都卡在 Topic 设计上。比较稳的设计方式，是先从治理维度倒推命名空间，再让代码按模板填充变量。常见结构可以写成 tenant/{tenantId}/product/{productKey}/device/{deviceId}/event/{eventType}，也可以根据平台风格压缩成 t/{tenantId}/p/{productKey}/d/{deviceId}/e/{eventType}。不管长短如何，关键是层级语义要稳定。

稳定的层级通常包含三类信息。第一类是隔离边界，例如租户、组织、项目、环境，便于 ACL 和统计口径按边界收敛。第二类是实体定位，例如产品、设备、网关、子设备，便于后端服务快速知道消息来自哪里。第三类是事件语义，例如 telemetry、property/post、status、command/reply、alarm，便于订阅端按职责选择自己要处理的消息。高频变化的业务状态值、完整属性对象、时间戳、签名、序列号、错误详情更适合放在 Payload 里，而不是继续塞进 Topic 层级。

一个常见反例是把 Topic 设计成 device/{deviceId}/{online}/{battery}/{temperature}。这种写法短期看起来直观，长期会让订阅过滤、权限配置和指标聚合都变得混乱。online、battery、temperature 是消息内容，不是命名空间骨架；如果它们进入 Topic，后端想订阅“所有设备状态变化”时会被迫写过宽的通配符，想统计“同一设备的状态流”时又要处理大量可变路径。

ACL 与可观测性依赖清晰 Topic ​

ACL 的本质是把“谁可以发布或订阅什么范围”表达成可维护的规则。Topic 层级越稳定，ACL 越容易写成有限的白名单；Topic 越随意，权限系统越容易退化成 # 或一堆难以审计的例外。例如设备端通常只允许发布自己的上行 Topic，只允许订阅自己的命令 Topic；规则引擎可以订阅某个租户下的遥测或告警；运维监控服务可以读取 $SYS/# 这类系统主题，但普通业务客户端不应该碰这些 Broker 内部主题。

可观测性也是同一个道理。Java 后端消费 MQTT 时，日志里至少要能看到 clientId、Topic Name、匹配的订阅配置、QoS、retain 标志、租户、产品、设备和事件类型。若 Topic 一开始就把这些维度放在固定层级，监控系统可以按层级做吞吐、失败率、延迟和积压分析；若 Topic 没有治理，排障时只能在 Payload 里反复解析，甚至不同设备固件还会用不同字段名表达同一概念。

二、Topic Filter 匹配规则与通配符边界 ​

/ 层级、大小写与零长度层级 ​

MQTT 使用 / 作为主题层级分隔符。factory/a/device/001/status 可以理解为五个层级：factory、a、device、001、status。分隔符本身会影响通配符匹配，所以 factory/+/status 只匹配三层结构，不会匹配 factory/a/device/status。Topic 匹配不是包含关系，也不是正则表达式，而是按层级逐段比较。

相邻的 / 会产生零长度层级。规范允许 Topic Name 和 Topic Filter 中出现这种结构，例如 factory//status 中间就有一个空层级。factory/+/status 可以匹配它，因为 + 匹配的是一个主题层级，而这个层级可以是零长度。工程上一般不建议主动设计空层级，因为它会让日志检索、路径展示、ACL 审计和人工排错都变得反直觉，但面试里要知道这不是简单的非法字符串。

前导 / 和尾随 / 也会形成不同 Topic。/finance、finance、finance/ 彼此不同；只包含 / 的 Topic Filter 也是合法的。物联网平台通常会约定不使用前导空层级，全部使用小写字母、数字和少量分隔符，并通过 SDK 或 Topic 模板生成，目的不是因为协议只支持这种写法，而是为了让团队共享同一套治理规则。

+ 单层通配符 ​

+ 是单层通配符，只能匹配一个 Topic 层级，并且必须独占整个层级。device/+/status 合法，可以匹配 device/001/status，也可以匹配 device//status；device/+abc/status 不合法，因为 + 没有独占一个完整层级。+ 可以出现在首层、末层和中间层，也可以出现多次，例如 tenant/+/device/+/status。

理解 + 的关键，是不要把它看成“任意字符串”。device/+ 不匹配 device，因为后者只有一层；但它可以匹配 device/，因为后者存在一个零长度的末层。这个细节经常出现在订阅范围过宽或过窄的排障里：后端以为自己订阅了“某前缀下所有状态”，实际上因为层级数量不一致漏掉了一类消息。

在 Java 后端里，+ 适合表达“某一层有多个取值，但结构固定”的场景，例如 tenant/t1/product/+/device/+/telemetry。它不适合表达复杂条件，例如“订阅电量小于 20 的设备”或“订阅固件版本大于某个值的设备”，这类条件应该放在 Payload 过滤、规则引擎或数据库查询里处理。

# 多层通配符与 $ 系统主题 ​

# 是多层通配符，表示父层级以及任意数量的子层级。它必须单独出现，或者紧跟在 / 后面，并且必须是 Topic Filter 的最后一个字符。device/# 合法，可以匹配 device、device/001、device/001/status；# 也合法，可以匹配普通应用主题；device/a# 和 device/#/status 都不合法。

# 很适合做有限边界内的兜底订阅，例如规则引擎订阅 tenant/t1/product/p1/device/+/event/#，表示接收某租户某产品下所有设备事件子类。但生产环境里让普通业务服务订阅裸 # 往往是危险信号：它会绕过租户、产品、事件类型等治理边界，也会让服务收到大量不相关消息。排障可以临时用宽订阅，长期运行的服务应该把订阅范围收窄到职责边界内。

以 $ 开头的 Topic Name 还有特殊规则。规范要求，以通配符 # 或 + 开头的 Topic Filter 不匹配以 $ 开头的 Topic Name。因此订阅 # 不会自动收到 $SYS/... 系统主题；如果要观察 Broker 指标，需要显式订阅 $SYS/#。这条规则可以把系统主题与应用主题隔离开，也提醒我们不要把业务 Topic 设计成 $ 前缀。

三、MQTT 5 Subscription Options：订阅不是只有 QoS ​

最大 QoS 与订阅选项字节 ​

在 MQTT 3.1.1 中，订阅项主要由 Topic Filter 和 Requested QoS 组成；到了 MQTT 5，每个订阅项后面有一个 Subscription Options 字节。这个字节的低两位仍然表示 Maximum QoS，也就是 Broker 给这个订阅下发应用消息时允许使用的最高 QoS。它不是发布端 QoS 的简单复制，而是“Broker 到当前订阅 Session”这一段链路的上限。如果发布端以 QoS 1 上报，而订阅端只被授予 QoS 0，Broker 转发给该订阅端时可以降级为 QoS 0。

Maximum QoS 的取值只能是 0、1、2，值为 3 是协议错误。后端项目里要特别注意 SUBACK 返回值，因为 Broker 可能授予比请求更低的 QoS，也可能因为权限、Topic Filter、能力限制等原因拒绝某个订阅。很多线上问题不是 SUBSCRIBE 没发出去，而是 SDK 没认真处理 SUBACK，导致服务以为自己已经按预期订阅，实际上 Broker 给的是失败码或降级后的 QoS。

Subscription Options 的剩余位引入了三个非常实用的语义：No Local、Retain As Published 和 Retain Handling。它们都作用在“这个订阅如何接收匹配消息”上，不改变发布端原始消息，也不改变其他订阅者的行为。理解这一点很重要，因为同一条 PUBLISH 命中多个订阅时，不同订阅可以因为选项不同而看到不同的 retain 标志、不同的初始化 retained 补发行为，甚至有的订阅会因为 No Local 跳过本连接发布的消息。

No Local 控制回环消息 ​

No Local 位用于避免消息回到同一个 ClientID 对应的发布连接。如果某个订阅把 No Local 设为 1，Broker 不应该把“发布连接 ClientID 等于该订阅连接 ClientID”的应用消息再转发给它。这个选项常见于 MQTT Bridge、边缘网关和双向同步场景：网关从上游 Broker 收到消息后转发到下游，再从下游订阅回传消息，如果没有 No Local 或类似去环策略，很容易把自己转发过的消息再次收到，形成回环。

No Local 的判断基于 ClientID，而不是基于业务里的 deviceId 或 Payload 字段。Java 后端如果多个实例使用不同 ClientID，即使它们属于同一个业务服务，No Local 也不会自动阻止实例之间收到彼此发布的消息。反过来，如果同一个 ClientID 在错误配置下被多个连接复用，Broker 还可能先踢掉旧连接，造成更复杂的会话问题。所以 No Local 解决的是协议连接层的回环，不是业务去重的替代品。

规范还明确限制：共享订阅不能把 No Local 设为 1，否则是协议错误。原因可以从语义上理解：共享订阅本来就是多个 Session 共同组成一个消费组，Broker 要在这些 Session 中选择一个投递目标；如果再按发布连接的 ClientID 做本地回环排除，会让共享组内的分配语义变得不清晰。需要避免共享订阅中的业务回环时，应使用消息来源标识、链路追踪 ID、幂等键或网关侧转发策略处理。

Retain As Published 与 Retain Handling ​

Retain As Published，简称 RAP，控制 Broker 转发普通匹配消息时是否保留原始 PUBLISH 的 RETAIN 标志。RAP 为 1 时，转发给该订阅的应用消息保持发布时的 retain 标志；RAP 为 0 时，Broker 转发普通应用消息时把 RETAIN 标志置为 0。需要注意，新订阅建立时补发的 retained messages 仍然以 RETAIN 标志为 1 发送，这一点不由 RAP 改写。

Retain Handling 控制的是“订阅建立这一刻是否补发 retained messages”，它不影响订阅建立之后新发布的 retained 消息。取值 0 表示订阅时发送匹配的 retained messages；取值 1 表示只有当前 Session 里原本不存在这个订阅时才发送，若只是重复订阅或修改已有订阅则不发送；取值 2 表示订阅时不发送 retained messages。取值 3 是协议错误。

这两个选项解决的是两个不同问题。RAP 关心“后续转发时 retain 标志是否保留发布端语义”，适合桥接和跨 Broker 同步；Retain Handling 关心“建立订阅时要不要拿当前状态快照”，适合控制 Java 服务重连后的初始化行为。把二者混在一起，容易误以为设置了 RAP 就能控制 retained 补发，或者误以为 Retain Handling 会改变未来消息的 retain 标志。

四、Retained 消息在订阅阶段如何影响初始化状态 ​

Retain Handling 三种取值的工程含义 ​

Retained Message 的价值是让新订阅者立刻获得某个 Topic Name 上的最新状态。比如设备不定期上报在线状态、固件版本、当前配置摘要，控制台或规则服务重新订阅时不必等待设备下一次主动上报，就可以先拿到 Broker 保存的最后状态。MQTT 5 的 Retain Handling 让订阅端可以更精细地控制这个初始化过程。

取值 0 最像传统行为：只要建立订阅，就把匹配的 retained messages 发过来。它适合控制台、状态缓存服务、规则引擎冷启动等场景，因为这些组件希望一启动就补齐当前状态。代价是重连或重复订阅时可能再次收到大量 retained 状态，业务处理链路必须能识别这是状态快照，而不是新的历史事件。

取值 1 适合会话恢复不确定的场景。客户端重连后可能不知道上一次订阅是否已经在 Session 中建立完成，如果直接重复订阅，取值 1 可以让 Broker 在“订阅已存在”时不重复补发 retained messages，在“订阅确实不存在”时再发送。取值 2 则适合只关心未来增量的消费者，例如高频遥测入库服务已经有自己的状态存储，不希望每次订阅都被 retained 快照冲击。

RAP 如何影响状态复制与桥接 ​

RAP 的典型场景是桥接。假设边缘 Broker 要把现场设备状态同步到云端 Broker，云端还要知道某条消息是不是原始 retained 状态。如果桥接订阅使用 RAP=1，边缘 Broker 转发给桥接客户端时保留 retain 标志，桥接客户端再发布到云端时可以按策略继续保留这个语义。若 RAP=0，桥接客户端看到的转发消息 retain 标志已经被清零，后续链路很难判断这条消息原本是不是 retained。

但在普通业务消费里，RAP=0 往往更容易处理。很多 Java 后端服务只关心收到一条状态更新，不希望后续每条由 retained 发布触发的转发都带着 retain 标志影响业务分支。此时可以把 retained 补发当作订阅初始化阶段的特殊情况处理，而把订阅建立后的普通转发统一视为实时消息。选择 RAP=0 还是 1，关键要看订阅端是否需要保留发布端的 retain 语义，而不是看 retained 功能本身是否开启。

还要注意，Retained Message 不是离线消息队列。它按 Topic Name 保存最后一条 retained 发布，解决“新订阅者看到最新状态”的问题；离线消息则跟 Session、QoS、会话过期和消息过期有关，解决“某个会话离线期间错过的匹配消息如何处理”的问题。状态类消息可以 retained，审计日志、告警流水、命令执行记录不能指望 retained 保存历史。

Java 后端处理 retained 初始化的边界 ​

Java 后端消费 MQTT 时，最好在消息模型里显式保留 topic、qos、retained、clientId、subscriptionIdentifier、receivedAt 和业务 Payload。对于 retained 初始化消息，处理逻辑通常要和实时事件区分开：状态缓存可以覆盖写，规则触发要避免把历史快照当作新告警，入库服务要用 eventId、reportedAt 或版本号判断是否旧状态覆盖新状态。

如果服务启动时订阅范围很宽，例如 tenant/+/product/+/device/+/status，Retain Handling=0 可能在短时间内带来大量 retained 快照。此时需要配合批量处理、限速、异步队列、线程池隔离和幂等写入，否则服务刚启动就可能被初始化状态压垮。若服务本地已有可靠状态库，启动时可以选择 Retain Handling=2，只处理后续变化；若状态库可能丢失或需要自愈，则可以保留补发，但要把它当作一次有控制的重建流程。

一个面试表达可以这样组织：Retained Message 负责“按 Topic 保存最新状态”，Retain Handling 负责“订阅建立时是否把这些状态发给我”，RAP 负责“后续转发时是否保留发布端 retain 标志”。三者都围绕 retained 语义，但分别作用在 Broker 存储、订阅初始化和转发标志三个不同位置。

五、共享订阅让多个 Session 分担匹配消息 ​

共享订阅格式与匹配语义 ​

共享订阅是 MQTT 5 标准化的订阅端横向扩展能力。它的 Topic Filter 采用 $share/{ShareName}/{filter} 格式，其中 $share 是固定前缀，{ShareName} 是共享组名，不能包含 /、+、#，并且至少一个字符；{filter} 才是真正用于匹配发布 Topic Name 的 Topic Filter，语法与普通订阅一致。匹配时，$share 和 {ShareName} 不参与对发布 Topic Name 的匹配。

例如三个 Java 消费实例都订阅 $share/rule-workers/tenant/+/device/+/event/#，它们的 Session 会加入同一个共享订阅。之后某条消息发布到 tenant/t1/device/d1001/event/alarm，Broker 发现它匹配共享订阅的 {filter}，但只会选择该共享订阅下的一个 Session 投递，而不是把同一条消息广播给三个实例。这样多个实例可以共同分担规则计算、入库、告警处理等可并行的后端任务。

共享订阅的重点是多个 Session 分担“同一个共享订阅”命中的消息，而不是改变 MQTT 的整体发布订阅模型。同一个客户端仍然可以同时拥有普通订阅和共享订阅；同一个 Broker 上也可以存在多个 ShareName 不同但 {filter} 相同的共享订阅。每个共享订阅彼此独立，某条消息如果同时命中两个共享组，会分别在两个组内各投递一份。

普通订阅、共享订阅与 retained 的关系 ​

普通非共享订阅更像广播：多个 Session 订阅同一个 Topic Filter，每个 Session 都会收到匹配消息。共享订阅更像消费组：多个 Session 订阅同一个 $share/{ShareName}/{filter}，每条匹配消息只交给其中一个 Session。这个差异决定了它们的使用场景：监控、缓存刷新、审计旁路适合普通订阅，因为每个系统都需要一份消息；规则计算、告警入库、任务处理适合共享订阅，因为同一业务动作通常只希望一个实例执行。

共享订阅还有一个容易被忽略的 retained 边界：建立共享订阅或新增 Session 加入共享订阅时，不发送 retained messages。即使只有一个 Session 订阅某个共享订阅，它在 retained 补发这件事上也不同于普通订阅。这个设计避免多个消费者加入共享组时反复处理同一批状态快照，但也意味着共享消费者不能依赖 retained 初始化全量状态。

因此在项目中，常见组合是用普通订阅或单独初始化流程加载状态快照，再用共享订阅处理后续事件流。例如状态服务用普通订阅 tenant/+/device/+/status 获取 retained 最新状态，规则处理服务用 $share/rule-workers/tenant/+/device/+/event/# 分担实时事件。不要指望共享订阅启动时自动补齐 retained 状态，也不要把共享订阅当成完整的 Kafka Consumer Group，因为 MQTT 标准不定义分区、offset、重平衡协议和历史回放。

负载均衡与失败处理的边界 ​

规范允许 Broker 在多个订阅 Session 中按自己的实现选择投递目标，可以轮询、随机、按负载、按连接状态或按其他策略。标准保证的是“一个共享订阅命中的一条应用消息只发给其中一个订阅 Session”，不保证严格均匀，也不保证按设备维度固定分配。需要按设备顺序处理时，不能只依赖共享订阅的分配算法，往往还要在业务侧按 deviceId 分片，或者使用 Broker/下游队列提供的顺序能力。

QoS 失败边界也要讲清楚。共享订阅中的每个订阅者可以请求不同 QoS，Broker 给每个客户端授予的最大 QoS 也可能不同，投递给某个客户端时必须遵守该客户端被授予的 QoS。若 QoS 1 消息已经选择某个 Session 投递，但连接在 ACK 前断开，Broker 可以等待该 Session 重连并重发，也可以在会话终止等情况下转给同一共享订阅的其他客户端，具体行为与 QoS 和会话状态有关。若业务要求严格一次处理，仍然要靠幂等键、唯一索引、状态机和去重表兜底。

共享订阅也可能制造重复处理的错觉。一个客户端如果既订阅普通 tenant/+/device/+/event/#，又加入 $share/rule-workers/tenant/+/device/+/event/#，某条消息同时命中二者时，它可能通过普通订阅收到一份，又作为共享组中被选中的 Session 再收到一份。排查重复消息时，除了看 QoS 重传，也要看订阅配置是否重叠。

六、从协议能力落到 Java 与物联网项目实践 ​

Subscription Identifier 提升客户端侧路由与观测 ​

MQTT 5 的 Subscription Identifier 可以让客户端在 SUBSCRIBE 中给订阅配置一个整数标识，取值范围是 1 到 268435455，0 是协议错误。Broker 保存这个标识后，后续转发由该订阅命中的 PUBLISH 时，会把对应的 Subscription Identifier 放进下发报文。若一条消息命中同一客户端的多个带标识订阅，Broker 可以把多个标识一并返回；若是共享订阅，只返回接收该消息的客户端在 SUBSCRIBE 中设置的标识。

这个能力对 Java 后端很有用。一个服务可能同时订阅设备状态、遥测、告警、命令回复和平台控制消息，如果只看 Topic，客户端需要在本地重新跑一遍 Topic Filter 匹配才能决定分发到哪个处理器；有了 Subscription Identifier，就可以直接把 101 映射到状态处理器，把 102 映射到告警处理器，把 201 映射到命令回复处理器。日志中记录这个标识，也能快速定位“是哪条订阅配置把消息引入了当前服务”。

它同样是观测手段，不是业务语义本身。不要把 Subscription Identifier 当成租户 ID、产品 ID 或消息类型 ID；这些业务字段仍然应该来自 Topic 层级或 Payload。Subscription Identifier 更像客户端内部订阅配置的编号，适合排障、路由和指标打点。混合版本环境里还要读取 CONNACK 的能力声明，确认 Broker 支持 Subscription Identifiers 后再启用。

Broker 能力声明决定客户端降级策略 ​

MQTT 5 允许 Broker 在 CONNACK 中声明一些订阅相关能力，例如是否支持 Wildcard Subscription、是否支持 Subscription Identifier、是否支持 Shared Subscription。若 Broker 明确声明不支持通配符订阅，客户端继续发送包含 + 或 # 的订阅就是协议错误或会收到订阅失败；若 Broker 不支持共享订阅，客户端发送 $share/... 也可能被断开或收到失败原因码。

工程上不要因为“连接成功”就默认所有 MQTT 5 特性都可用。Java SDK 建连后应该记录 Broker 返回的能力，并把它纳入订阅构建逻辑：支持共享订阅时使用 $share/{group}/{filter} 横向扩展；不支持时降级为单消费者、多个普通订阅或转接到下游队列；支持 Subscription Identifier 时开启订阅标识打点，不支持时退回本地 Topic Filter 匹配；支持通配符订阅时使用有限范围的 + 和 #，不支持时改为展开具体 Topic 或调整接入模型。

这种能力协商也能改善告警质量。订阅失败时，日志不应只写“MQTT subscribe failed”，而要记录协议版本、ClientID、Topic Filter、共享组名、请求 QoS、订阅选项、SUBACK Reason Code、Broker 能力声明和当前配置来源。这样排障人员可以区分是 ACL 拒绝、Topic Filter 非法、Broker 不支持共享订阅，还是订阅选项组合错误。

落地时把 Topic、ACL、消费组和指标一起设计 ​

一个可维护的物联网 MQTT 后端，通常会把 Topic 模板、ACL 模板、订阅配置和观测指标放在同一张设计图里。设备 SDK 只允许按模板发布和订阅自己的 Topic；后端服务按职责订阅有限范围；共享订阅用于可横向扩展的工作负载；普通订阅用于每个系统都要接收一份的旁路链路；Retain Handling 用于控制启动阶段是否加载状态快照；No Local 和 RAP 用于桥接和回环控制；Subscription Identifier 用于客户端侧分发和排障。

落地检查可以抓住几条主线。Topic 是否能按租户、产品、设备、事件类型稳定拆分；ACL 是否能用这些层级写成少量白名单；生产服务是否避免裸 #；共享订阅是否只用于“同一业务动作只处理一次”的场景；retained 是否只用于最新状态而不是历史事件；订阅重叠是否会导致同一客户端收到多份消息；日志和指标是否能看到 Topic、订阅标识、共享组、QoS、retain 标志和处理结果。

面试或项目复盘时，可以把这一篇压缩成一句主线：Topic 设计决定 MQTT 系统能不能治理，Topic Filter 决定消息如何匹配，订阅选项决定匹配后如何投递 retained 与回环消息，共享订阅决定多个 Session 如何分担同一类消息，ACL 与可观测性则要求这些设计从一开始就可命名、可授权、可统计、可排障。
