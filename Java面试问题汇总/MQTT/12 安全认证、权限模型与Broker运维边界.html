12 安全认证、权限模型与 Broker 运维边界 ​

MQTT 的安全不能简化成“开 TLS 就安全”。TLS 解决的是网络链路上的机密性、完整性和服务端身份校验，最多再通过双向 TLS 承载客户端证书身份；但它不自动知道某个设备能不能发布 tenant/t1/device/d1/telemetry，也不自动判断某个 Java 消费服务是否可以订阅 tenant/+/device/+/command/#。真正的 MQTT 安全，要把传输加密、客户端身份、认证材料、Topic 级授权、Broker 插件、证书生命周期、审计日志和连接治理放在同一条链路中理解。

官方 FAQ 给了最基础的边界：TCP 1883 是 MQTT 常用标准端口，TCP 8883 用于 MQTT over SSL/TLS；Broker 是接收发布消息并把消息路由给订阅者的服务器；用户名和密码可以跟随 MQTT 连接报文传递，而网络加密由 SSL/TLS 在 MQTT 协议之外完成。MQTT 5 规范又继续补充了 Authentication Method、Authentication Data、AUTH 控制报文、Server Reference、Maximum Packet Size、Wildcard Subscription Available、Shared Subscription Available 等能力。它们让客户端和 Broker 能表达更多连接能力与认证过程，但 Topic ACL、租户隔离、证书吊销、规则引擎权限、审计留痕等通常仍是 Broker 产品或平台侧实现。

images/mqtt-12-security-acl-broker-boundary.png

这张图可以按“入口连接 -> 身份认证 -> Topic 授权 -> Broker 运维边界”来读。客户端先通过 1883、8883、WebSocket 或其他监听入口接入 Broker；Broker 再根据 TLS、ClientId、用户名密码、证书、Token 或增强认证机制识别连接身份；身份确认后，ACL 决定该连接能发布、订阅、保留、共享订阅或访问系统主题的 Topic 范围；最后，运维层继续处理证书轮换、连接数、限速、断线风暴、审计日志、集群迁移和插件稳定性。协议定义的是报文和交互规则，生产可用的安全边界来自这些规则与 Broker 工程能力的组合。

一、安全分层：MQTT 规范不是完整安全产品 ​

1883、8883 与 TLS 的位置 ​

1883 与 8883 经常被面试题和配置文件放在一起问，但它们不是“安全开关”的全部含义。1883 通常表示普通 MQTT over TCP，报文内容在网络上明文传输；8883 通常表示 MQTT over TLS，先建立 TLS 安全通道，再在通道里传输 MQTT 控制报文。TLS 能防止旁路监听者直接读取 Topic、Payload、用户名密码和控制报文，也能通过证书链校验服务端身份，避免客户端连到伪造 Broker。

但是 TLS 不等于业务授权。客户端连上 8883，只能说明网络链路被加密，并不说明这个客户端有权订阅所有 Topic。如果 Broker 配置允许匿名连接、ACL 规则过宽，或者所有设备共用同一组用户名密码，那么攻击者拿到任意一份凭据后，仍然可能在加密通道内发布伪造命令或订阅其他租户的数据。安全设计要把“链路有没有加密”和“连接是谁、能做什么”分开。

TLS 也有部署成本。设备端要保存 CA 根证书或证书链，Broker 要配置服务端证书与私钥，双向 TLS 还要管理每个设备或每批设备的客户端证书。证书过期、域名不匹配、时间不同步、证书链不完整，都会表现为连接失败。很多线上问题不是 MQTT 协议错，而是 TLS 握手阶段已经失败，所以排障时要先区分“TCP 建连失败、TLS 握手失败、MQTT CONNECT 被拒绝、SUBSCRIBE 被拒绝”这几个层次。

Broker 是安全控制面，不只是转发器 ​

MQTT Broker 在安全链路里不是一个透明管道。它接收所有客户端连接，解析 CONNECT、SUBSCRIBE、PUBLISH 等控制报文，维护会话、订阅表、保留消息、遗嘱消息、共享订阅分组和系统状态。也正因为所有消息都要经过 Broker，Broker 才成为认证、鉴权、审计、流控和隔离的关键控制面。

从发布订阅模型看，发布者并不知道订阅者是谁，订阅者也不直接连接发布者。这个解耦提升了伸缩性，但也意味着权限必须落在 Broker 上：发布端能不能向某个 Topic Name 写入，订阅端能不能用某个 Topic Filter 读取，保留消息能不能被设置，共享订阅能不能加入，桥接连接能不能转发跨集群 Topic，都要在 Broker 或其外部鉴权服务中判断。

工程上常见的错误，是把 Broker 当作“内网组件”而忽略安全边界。只要有设备、网关、移动网络、第三方平台或跨云桥接，Broker 就不再只是内部队列。它既暴露长连接入口，又持有大量设备在线状态和订阅关系；一旦认证鉴权过宽，攻击面会沿 Topic 命名空间横向扩散。

协议规范与产品扩展要分开说 ​

MQTT 规范定义的是客户端与服务端如何编码、发送、确认和拒绝控制报文。比如 CONNECT 报文可以携带 Client Identifier、User Name、Password；MQTT 5 可以用 Authentication Method 与 Authentication Data 表达增强认证机制；AUTH 控制报文用于挑战响应式的扩展认证交换；CONNACK 可以返回服务端能力或拒绝原因。这些是协议层可以共同理解的结构。

但“用户名密码存在哪里、密码是否加盐哈希、Token 如何校验、证书 Subject 如何映射设备、ACL 如何持久化、是否支持按租户调用外部 HTTP 鉴权、是否能对规则引擎再做权限隔离”，这些通常不是 MQTT 协议统一规定的，而是 Mosquitto、EMQX、HiveMQ、云 IoT Broker 或企业自研平台的实现扩展。面试和项目复盘中要明确表达：MQTT 提供认证字段和扩展认证交互，Broker 产品实现具体认证源、授权策略和运维能力。

规范中的 Security 章节本身也是非规范性分析，适合用来理解风险面，而不是当作具体产品配置手册。真正落地时，要同时看协议规范、Broker 官方配置文档、企业证书管理规范、网络暴露策略和审计合规要求。

二、连接入口：客户端身份不是只有用户名密码 ​

CONNECT 中的 ClientId、User Name 与 Password ​

MQTT 连接从 CONNECT 报文开始。ClientId 用来标识一个 MQTT 客户端会话，影响会话状态、离线消息、订阅恢复和同名连接挤下线等行为；User Name 和 Password 是连接认证材料，服务端可以据此判断是否接受连接。规范层面只规定这些字段如何出现在报文中，并规定标志位与载荷字段要一致：用户名标志位为 1 时必须带 User Name，密码标志位为 1 时必须带 Password；标志位为 0 时相应字段不能出现。

这里要注意两个边界。第一，ClientId 不天然等同于认证身份。很多 Broker 会把 ClientId 纳入认证或授权判断，例如要求设备只能用自己的 ClientId 连接，但协议本身不会证明“持有这个 ClientId 的连接就是这个设备”。第二，User Name 和 Password 如果走 1883 明文链路，会直接暴露在网络中；即使走 TLS，也要避免所有设备共用同一密码，否则单点泄露会变成批量设备失陷。

生产设计通常会把 ClientId、用户名、设备编号、租户、产品和证书主体建立映射。比如设备连接时使用 clientId=deviceId，用户名携带产品或租户标识，密码使用设备密钥签名出的短期摘要；Broker 或认证插件校验签名后，把连接身份绑定到 tenantId/productKey/deviceId。这样后续 ACL 才能判断该连接只能发布自己的上行 Topic，只能订阅自己的下行命令 Topic。

证书、Token 与双向 TLS ​

TLS 至少可以做服务端认证：客户端校验 Broker 证书，确认自己连的是可信服务端。若启用双向 TLS，Broker 还会校验客户端证书，用证书链、证书指纹、Subject、SAN 或自定义扩展字段识别设备。对物联网设备来说，客户端证书比静态密码更适合做批量设备身份管理，因为每个设备可以拥有独立证书，泄露后也可以单独吊销或禁用。

Token 方式常见于云平台、网关和 Java 服务端客户端。客户端连接前从业务系统获取短期 Token，连接时通过 Password、User Name 或认证数据传给 Broker，Broker 插件再调用本地缓存、JWT 验签、OAuth2 introspection、HTTP 鉴权服务或数据库校验。Token 的优势是可过期、可撤销、可携带租户与权限声明；风险是 Token 校验链路本身要可用，否则认证服务抖动会放大为 MQTT 大面积连接失败。

证书和 Token 也可以组合。设备用证书证明硬件身份，平台根据证书映射出设备记录，再下发短期访问 Token 或会话权限；服务端 Java 消费者使用企业身份系统签发的 Token 接入 Broker。这样能把“设备身份”和“业务权限”分层管理，避免把所有安全能力压到一个长期密码上。

MQTT 5 增强认证与 AUTH 报文 ​

MQTT 5 的增强认证把认证过程从“一次 CONNECT 携带凭据”扩展为可协商的认证交换。客户端在 CONNECT 中使用 Authentication Method 指明认证方法，并用 Authentication Data 携带该方法需要的初始数据；如果认证方法需要挑战响应，客户端和服务端可以继续通过 AUTH 控制报文交换认证数据。AUTH 报文可以由客户端或服务端发送，属于扩展认证流程的一部分。

这个机制给 SASL、挑战响应、二次认证、会话内重新认证等场景留下空间。比如服务端可以先返回挑战随机数，客户端用设备密钥签名后通过 AUTH 回传；也可以在连接持续很久时触发重新认证，避免长连接无限期持有旧权限。规范规定，如果 CONNECT 没有包含相同的 Authentication Method，客户端或服务端不应随意发送 AUTH 报文，否则属于协议错误。

增强认证并不替代 Broker 插件。协议只定义“认证方法名”和“认证数据如何在 MQTT 报文中传递”，不定义每种方法的密码学细节，也不定义认证数据库在哪里。因此文档表达时要说清：MQTT 5 提供增强认证的报文机制，具体采用 SCRAM、JWT、OAuth、设备签名还是企业自定义挑战响应，是 Broker 与客户端共同约定的实现。

三、Topic 级授权：ACL 决定连接能触达哪里 ​

发布权限和订阅权限要分别建模 ​

认证回答“你是谁”，授权回答“你能做什么”。在 MQTT 中，授权最核心的对象是 Topic，但发布和订阅必须分开判断。发布端提交的是 Topic Name，例如 tenant/t1/product/p1/device/d1/telemetry；订阅端提交的是 Topic Filter，例如 tenant/t1/product/p1/device/+/telemetry。Broker 应分别校验当前连接是否有权向该 Topic Name 发布，以及是否有权使用该 Topic Filter 订阅。

设备端的最小权限通常很窄：允许发布自己的遥测、属性上报、事件、命令响应；允许订阅自己的命令、配置下发、OTA 通知；不允许订阅同租户其他设备的数据，更不允许订阅裸 #。Java 后端消费者的权限可以按服务职责扩大，例如规则引擎服务订阅某租户下全部遥测，告警服务订阅告警事件，设备影子服务订阅属性上报和命令响应，但也不应默认拥有所有 Topic 的读写权限。

ACL 还要覆盖 retained message、Will Message、共享订阅、系统主题和桥接转发。比如设备能不能发布 retained 状态，能不能设置遗嘱 Topic，服务能不能订阅 $SYS/#，桥接连接能不能把远端 Topic 写入本地租户命名空间，这些都可能成为越权入口。只给 PUBLISH/SUBSCRIBE 做粗粒度判断，往往挡不住真实系统里的权限绕行。

通配符越权是 MQTT 最常见的权限事故 ​

Topic Filter 的 + 和 # 给订阅带来灵活性，也给权限带来风险。tenant/t1/# 看起来只是订阅一个租户，实际会覆盖该租户下所有产品、设备、事件、命令、响应和可能的内部主题；tenant/+/device/+/telemetry 看起来像统一遥测入口，实际可能跨租户读取数据。若 Broker 的 ACL 只做字符串前缀判断，很容易把过宽通配符误放给普通客户端。

好的 ACL 应该按 Topic 层级语义判断，而不是只看字符串是否“像某个前缀”。设备 d1 可以订阅 tenant/t1/product/p1/device/d1/command/#，但不应订阅 tenant/t1/product/p1/device/+/command/#；租户级后端服务可以订阅 tenant/t1/product/+/device/+/telemetry，但不应订阅 tenant/+/product/+/device/+/telemetry；运维账号临时排障可以申请宽订阅，但要有审批、有效期和审计。

以 $ 开头的系统主题也要单独管理。规范中，普通以通配符开头的订阅不会自动匹配 $ 开头的 Topic，因此订阅 # 不会自然收到 $SYS/#。这降低了系统主题被普通宽订阅读到的风险，但并不意味着可以把 $SYS/# 暴露给所有客户端。系统主题可能包含连接数、吞吐、订阅数量、版本、节点状态等信息，攻击者拿到后可以更准确地选择攻击窗口。

共享订阅的权限边界要按组和真实 Topic 双重校验 ​

共享订阅把多个 Session 放进同一个消费组，Topic Filter 常见形式是 $share/{group}/{filter}。Broker 收到匹配消息后，从共享组中选择一个订阅者投递，用来让多个后端实例分摊消息。共享订阅提升了消费伸缩性，但也把权限边界变复杂：权限判断不能只看 $share/{group}，还必须看后面的真实 Topic Filter。

例如某服务订阅 $share/rule-engine/tenant/t1/product/+/device/+/telemetry 是合理的租户内横向扩展；如果它能订阅 $share/rule-engine/tenant/+/product/+/device/+/telemetry，就可能读取其他租户数据。更隐蔽的问题是共享组名本身也可能成为冲突点：两个业务如果误用同一个 group 和相同过滤条件，消息会被分摊到不同服务实例，表现为双方都“偶发漏消费”。因此共享订阅的授权要同时检查 group 命名、Topic Filter 范围和服务身份。

MQTT 5 的 Shared Subscription Available 让服务端可以在 CONNACK 中声明是否支持共享订阅。如果 Broker 声明不支持，客户端继续使用共享订阅就是协议错误。这个字段表达的是服务端能力，不是完整授权；即使服务端支持共享订阅，也仍然需要 ACL 决定哪些客户端能使用共享订阅、能加入哪个共享组、能订阅哪些真实 Topic。

四、MQTT 5 能力声明：安全治理可以前移到协商阶段 ​

Maximum Packet Size 限制单包攻击面 ​

Maximum Packet Size 不是认证字段，但它与安全治理密切相关。客户端可以在 CONNECT 中声明自己能接收的最大控制报文大小，Broker 可以在 CONNACK 中声明服务端能接收的最大控制报文大小。规范要求发送方不要向对方发送超过其限制的包；如果收到超限包，接收方可以按协议错误处理，并使用 Packet too large 这类原因码断开连接。

安全角度看，它能降低超大 Payload、超长属性、异常 User Property 或恶意构造报文对解码内存和规则引擎的冲击。没有单包上限时，一个客户端可能用低频但超大的 PUBLISH 让 Broker 解码、复制、持久化和转发链路承压；有上限后，Broker 可以在入口处尽早拒绝不符合资源边界的报文。

但它仍不是 QPS 限流，也不是总带宽限制。攻击者可以发送大量小包绕过单包上限，所以 Broker 还要配合连接速率限制、每连接发布速率、租户配额、Topic 级限速和下游背压。面试里可以说：Maximum Packet Size 是单个 MQTT 控制报文的资源边界，保护的是解码和内存峰值；吞吐治理还要靠 Broker 产品能力。

Wildcard 与 Shared Available 是能力声明，不是权限授予 ​

MQTT 5 的 Wildcard Subscription Available 表示服务端是否支持通配符订阅，Shared Subscription Available 表示服务端是否支持共享订阅。若服务端在 CONNACK 中声明某能力不可用，客户端继续使用相应能力会构成协议错误。这两个字段给 Broker 提供了把高风险能力前移到连接协商阶段的手段。

例如某些多租户或边缘场景中，Broker 可以对设备入口禁用通配符订阅，要求设备只能订阅精确 Topic，从而减少误订阅和越权范围；对普通设备禁用共享订阅，避免设备伪装成消费组成员；对后端服务入口开放通配符和共享订阅，但通过 ACL 控制具体范围。这样一来，不同监听器、不同租户或不同客户端类型可以获得不同能力。

要再次强调，能力声明不是权限授予。Broker 声明支持通配符，并不代表某客户端可以订阅 #；Broker 声明支持共享订阅，也不代表任何客户端都能加入任意 $share 组。能力声明回答“这个协议特性在当前连接上能不能用”，ACL 回答“你在这个特性下能访问哪些 Topic 和资源”。

Server Reference 支持迁移、分流与重定向 ​

MQTT 5 的 Server Reference 允许服务端在 CONNACK 或 DISCONNECT 中告诉客户端另一个可使用的服务端地址，常见于服务器重定向、集群迁移、灰度分流或设备预配。配合原因码 Use another server、Server moved，Broker 可以引导客户端连接到更合适的节点或区域。

从安全角度看，Server Reference 不能被当成无条件跳转。客户端应只接受可信 Broker 给出的重定向，并继续对新地址做 TLS 证书校验、域名校验和认证流程。如果客户端盲目相信任意 Server Reference，就可能被诱导连接到恶意 Broker。Broker 侧也要避免把内部节点地址、管理域名或跨租户入口误返回给普通客户端。

运维上，Server Reference 可以降低迁移时的硬切风险，但需要客户端 SDK 正确处理 DISCONNECT 原因码和重连策略。若大量客户端同时收到迁移指令并立即重连到新节点，会形成重连洪峰。因此重定向策略要配合退避、批次、区域就近、连接上限和监控告警使用。

五、Broker 实现边界：插件、证书轮换与多租户治理 ​

认证鉴权插件是扩展点，也是故障点 ​

大多数生产 Broker 都会提供认证鉴权扩展点：本地密码文件、数据库、Redis、HTTP 回调、LDAP、JWT、公有云 IAM、Kubernetes 身份、企业自研插件等。它们让 MQTT 可以接入现有账号体系和设备管理平台，但也把 Broker 的可用性与外部鉴权链路绑定在一起。

插件设计要考虑三件事。第一是性能，长连接重连风暴时，认证请求会集中打到外部服务；若每次 SUBSCRIBE 和 PUBLISH 都实时查库，消息吞吐会被鉴权后端拖住。第二是缓存，认证结果和 ACL 可以短期缓存，但缓存要有过期、吊销和租户隔离，不能让已禁用设备长期保持旧权限。第三是失败策略，鉴权服务超时时是拒绝新连接、使用旧缓存，还是进入只读降级，要根据业务风险明确配置。

协议层只看到 CONNACK、SUBACK、PUBACK 或 DISCONNECT 的原因码；产品实现层才决定背后调用哪个插件、如何记录错误、如何统计拒绝率。排障时不能只看客户端“连接被拒绝”，要追到 Broker 认证日志、插件返回码、外部鉴权服务延迟和缓存命中率。

设备证书轮换要有重叠窗口 ​

设备证书不是发下去就结束。证书会过期，设备会报废，私钥可能泄露，CA 可能迁移，生产批次可能需要隔离。证书生命周期至少包含签发、烧录或下发、激活、轮换、吊销、禁用和审计。对离线时间长、网络质量差、时钟不准的设备，证书轮换尤其容易出问题。

比较稳的做法，是设计新旧证书重叠窗口。平台先允许同一设备在短期内使用旧证书和新证书之一连接，设备拿到新证书后完成切换并上报确认，平台再逐步禁用旧证书。若强制某一时刻全量切换，离线设备、低电量设备和弱网设备会在下一次上线时集体失败，运维上很难区分是证书过期、时间错误还是网络故障。

吊销也要能落到 Broker。仅在设备管理数据库里把设备标记为禁用，如果 Broker 的认证缓存没有刷新，设备可能继续保持连接或继续重连成功。生产环境要明确：禁用设备是否立即踢下线，已建立连接是否重新认证，证书吊销列表或 OCSP 是否可用，Broker 集群各节点多久同步吊销状态。

多租户边界不能只靠命名约定 ​

Topic 命名空间是多租户隔离的底座，但不能只靠开发自觉。租户 ID、产品 ID、设备 ID 如果只是字符串拼接，任何拿到发布权限的客户端都可能伪造另一个租户前缀。正确做法是让 Broker 在认证后得到连接所属租户和设备身份，再由 ACL 模板动态生成允许范围，而不是相信客户端传来的 Topic 前缀。

规则引擎、桥接、持久化和管理 API 也要纳入租户边界。一个规则如果能订阅全局 # 再把消息写入外部 HTTP，等于绕过普通客户端 ACL；一个桥接连接如果可以把远端 Topic 原样写入本地根命名空间，可能造成跨环境污染；一个管理账号如果能查看所有连接和订阅，也需要审计和最小权限。

因此，Broker 运维边界要从“客户端权限”扩展到“平台组件权限”。设备、移动端、Java 后端服务、规则引擎、桥接连接、监控账号、管理员账号都应使用不同身份和不同 ACL，不能共享一个超级账号。超级账号只适合短期维护，不适合长期跑业务。

六、运行治理：审计、指标、断线风暴与连接数 ​

运维指标要覆盖连接、认证、授权和消息路径 ​

MQTT 的运行指标不能只看 Broker 进程是否存活。连接侧要看当前连接数、新建连接速率、断开速率、TLS 握手失败数、CONNACK 拒绝原因、认证耗时、重连间隔分布和同 ClientId 踢下线次数。授权侧要看 SUBSCRIBE 拒绝数、PUBLISH 拒绝数、通配符订阅数量、共享订阅组数量、系统主题访问尝试和 ACL 命中情况。消息侧要看入站发布速率、出站投递速率、QoS 1/2 在途数量、会话队列积压、丢弃原因、超大包拒绝和下游规则引擎延迟。

这些指标要能按租户、产品、客户端类型、监听器、Broker 节点和 Topic 前缀聚合。否则告警只会告诉你“Broker 压力高”，却无法判断是某批设备固件重连、某个租户上报异常、某个后端消费组变慢，还是某个 ACL 变更导致大量订阅失败。

Java 后端也要接入同一套观测。消费服务应记录 ClientId、订阅过滤器、共享组、收到的 Topic、QoS、消息大小、处理耗时、业务失败原因和重试次数。Broker 认为消息已经投递，不代表业务已经处理完成；若后端回调线程阻塞，ACK 延迟、会话积压和业务超时会互相放大。

审计日志要能还原越权路径 ​

安全事件发生后，最重要的问题不是“有没有日志”，而是日志能不能还原路径。连接审计至少要记录时间、源 IP、监听器、TLS 信息、ClientId、认证主体、认证方式、结果和失败原因。授权审计要记录 PUBLISH/SUBSCRIBE/UNSUBSCRIBE 的 Topic 或 Topic Filter、动作、授予或拒绝结果、匹配到的 ACL 规则、租户和产品维度。管理审计要记录谁改了监听器、证书、认证源、ACL、规则引擎、桥接和集群配置。

审计日志要避免两个极端。一个极端是只记错误，不记成功；这样无法还原攻击者在成功认证后做了什么。另一个极端是把完整 Payload、密码、Token、证书私钥或敏感业务字段写入日志；这样日志系统本身会变成新的泄露面。比较合适的做法是记录安全决策所需的元数据和摘要，敏感字段脱敏或哈希化，必要时把高风险操作单独送入安全审计系统。

对于 Topic 越权，审计要能回答：哪个认证主体在什么时间用哪个 ClientId 发起了哪个 Topic Filter，Broker 为什么授予或拒绝，是否命中了通配符，是否加入了共享订阅组，后续是否收到跨租户消息。没有这条链路，#、+ 和 $share 带来的权限事故很难复盘。

断线风暴与连接数治理是安全问题也是稳定性问题 ​

MQTT 长连接系统最怕断线风暴。一次网络抖动、证书过期、DNS 切换、Broker 重启、认证服务故障或移动运营商 NAT 波动，都可能让大量设备同时断开并重连。重连时每个客户端都要经历 TCP、TLS、MQTT CONNECT、认证、会话恢复、订阅恢复和离线消息投递，压力会集中打到 Broker、认证服务、持久化存储和 Java 后端。

治理断线风暴要从客户端和 Broker 两侧同时做。客户端要有指数退避、随机抖动、最大重连间隔、失败原因区分和证书时间校验；不要所有设备固定每 1 秒重连一次。Broker 要有限制每秒新连接数、每 IP 或每租户连接数、认证并发、会话恢复速率、离线队列投递速率和共享订阅再均衡节奏。对已知迁移或维护，要分批重定向或滚动重启，避免把所有客户端赶到同一个时间点重连。

连接数治理也不是越大越好。每个连接都有 TCP 状态、TLS 会话、MQTT 会话、订阅关系、在途消息、心跳定时器和可能的离线队列。连接数上限要结合节点内存、CPU、文件描述符、网络带宽、认证服务容量、Topic 匹配成本和持久化能力估算。面试中可以这样表达：MQTT 安全的最后一层是运维边界，既要防未授权访问，也要防授权客户端因为重连、超大包、宽订阅或慢消费把 Broker 拖垮。
