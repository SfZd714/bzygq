# 文档解析、Chunk切分与Metadata设计

**文档解析、Chunk切分与Metadata设计**

RAG 系统的问答质量，表面上看是模型回答得准不准，往前追一层是检索结果准不准，再往前追一层就是知识库里的内容干不干净、切得合不合理、来源能不能追溯。文档解析、Chunk 切分和 Metadata 设计，就是 RAG 知识库构建的基础层。

很多初学者容易把这一步理解成“把文档读出来，然后向量化”。真实项目里没有这么简单。企业知识来源可能是 PDF、Word、Excel、网页、Markdown、扫描件，也可能是业务系统导出的工单、制度、公告和接口文档。它们的结构、排版、字段含义、权限范围都不一样，如果不先处理好，向量库里存进去的就不是知识，而是一堆带噪声的文本碎片。

这一节重点不是背工具名，而是理解三个问题：文档解析为什么会影响召回上限，Chunk 为什么不能随便按字数切，Metadata 为什么是企业 RAG 能做权限、引用和排查的关键。

 RAG 上限

RAG 的核心链路是“检索到依据，再让模型基于依据回答”。这意味着模型最终能看到什么，首先取决于知识库里存了什么。文档处理如果出了问题，后面检索、Rerank 和 Prompt 都是在错误底座上补救。

这张图要表达的是：不同文档格式带来的问题并不一样。PDF 常见问题是多栏排版、表格错乱和扫描件 OCR 错误；Word 常见问题是标题层级、批注、页眉页脚混入正文；Excel 的难点是合并表头、跨 Sheet 关系和字段含义；HTML 容易混入导航、脚注和重复内容；系统导出数据通常字段很多，但缺少自然语言解释。它们如果被直接切分和向量化，就会把噪声一起写进知识库。

所以，文档处理不是一个可有可无的预处理步骤，而是决定知识库质量的入口。解析阶段丢掉章节，检索时就难以定位来源；清洗阶段没有去掉重复页眉，向量里就会混进高频噪声；表格被拆乱，制度里的关键条件就可能失去上下文。RAG 的很多“答错”，本质上不是生成错了，而是模型拿到的依据从一开始就不完整。

 Pipeline：不是读取文件后直接入库

一个比较稳的文档处理流程，通常会经历文档接入、解析抽取、结构清洗、Chunk 切分、Metadata 标注、Embedding 入库和入库验收几个阶段。它的目标不是把文件变成一长段纯文本，而是把资料加工成可检索、可过滤、可追溯的知识单元。

![](https://hxsay.com:19000/hxsay-image/quesion/imgs/ddd29aecfec14708a80cd89742cc8566.png?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=admin_20260624_us-east-1_s3_aws4_request&X-Amz-Date=20260624T113214Z&X-Amz-Expires=604800&X-Amz-SignedHeaders=host&X-Amz-Signature=a90ec7b294e260b0ad4faceb59d18917fa338cb62829b43e6a61fa92b6fd5806)

文档接入阶段要记录原始文件、版本、分类和权限范围。解析抽取阶段要尽量保留标题、段落、列表、表格、图片说明和页码位置。结构清洗阶段要去掉页眉页脚、目录噪声、重复水印、空行和无意义符号，同时避免把有业务含义的字段误删。Chunk 切分阶段要把长文档拆成语义相对完整的片段。Metadata 标注阶段要为每个片段补上来源、章节、页码、版本、权限等结构化信息。最后才是生成向量、写入索引，并做抽样验收。

这里的“入库验收”很重要。很多系统只要程序跑完、向量写入成功，就默认建库完成。但工程上更应该抽查解析结果、Chunk 边界、Metadata 字段和向量召回效果。否则系统上线后出现问题时，很难判断是解析错、切分错、召回错，还是模型生成错。

# 三、文档解析：要保留结构，而不是只提取文字

文档解析的目标，不只是把文件变成文本，而是尽量保留原文的结构关系。对于制度类文档，标题、章节、条款、表格、附件和脚注都可能影响答案含义；对于技术文档，接口名、参数表、错误码和示例代码都有独立语义；对于业务文档，生效时间、适用范围、部门和版本可能比正文某一句话还关键。

如果解析后只剩一串平铺文本，系统就很难知道某句话属于哪个章节，也无法在回答里给出可靠引用。例如“报销上限为 500 元”这句话，如果丢掉前面的“市内交通费”标题，模型可能会把它误用到住宿费、差旅费或办公采购场景里。看起来只是少了一个标题，实际上已经改变了知识的适用范围。

因此，解析时至少要关注六类结构：标题层级、段落顺序、表格结构、页眉页脚、图片扫描件、附件脚注。标题层级决定后续能不能按章节切分和定位来源；段落顺序错乱会直接破坏语义；表格结构经常承载制度条件和数值；页眉页脚是高频噪声；扫描件需要 OCR 或多模态解析；附件和脚注则可能决定答案依据是否完整。

 切分：把长文档切成可召回的知识单元

Chunk 是文档被切分后的文本块。Embedding 模型通常不会对整本文档生成一个向量，而是对每个 Chunk 生成向量。这样做有三个原因：第一，长文本会让一个向量混入多个主题，语义表达变得模糊；第二，在线问答不能每次把整本文档都塞进上下文；第三，检索结果需要定位到具体依据，而不是把整份制度丢给模型。

![](https://hxsay.com:19000/hxsay-image/quesion/imgs/6f2ded93f0bd4560a8ac361a45aa4702.png?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=admin_20260624_us-east-1_s3_aws4_request&X-Amz-Date=20260624T113214Z&X-Amz-Expires=604800&X-Amz-SignedHeaders=host&X-Amz-Signature=977152ef05a1bdcf81ca10355dff944e193ae8d1d2f09c653ed9436932b0ced8)

常见切分方式可以按“规则简单程度”和“语义保留能力”来理解。固定长度切分实现最简单，但容易把一句话、一个条款或一个表格切断；递归切分会优先按标题、段落、句子逐级拆分，是很多项目的基础方案；结构切分更适合制度、手册和报告，因为它能利用标题、条款、列表和表格边界；语义切分会根据句段相似度判断边界，完整性更好但成本更高；LLM 辅助切分更灵活，但成本、稳定性和可复现性都需要评估。

基础项目里更推荐“结构切分 + 递归切分 + 适当 overlap”。先尽量尊重文档结构，按标题、条款、段落和表格边界切；如果某个块仍然过长，再递归切成更小片段；为了避免边界处语义断裂，可以保留一定 overlap。这样做不是追求复杂，而是在可控成本下尽量保留原文语义。

 大小：不是越大越完整，也不是越小越精准

Chunk 大小没有一个永远正确的数值。它取决于文档类型、Embedding 模型、检索方式、上下文窗口、问题类型和答案需要的证据跨度。真正要避免的是两个极端：一个 Chunk 太大，里面混入多个主题，召回结果不够聚焦；一个 Chunk 太小，只保留孤立句子，模型拿不到必要上下文。

images/rag\_chunk\_size\_tradeoff\_redraw.png

可以把 Chunk 大小看成一个召回粒度问题。过大的 Chunk 像把整页内容都塞进一个袋子，用户问某个细节时，向量可能被多个主题拉偏；过小的 Chunk 像把知识拆成碎片，用户问流程、条件或例外情况时，模型只看到局部。Overlap 的作用是缓解边界断裂，但 overlap 过大又会造成索引膨胀、召回重复和上下文浪费。

工程上通常不是一次决定 Chunk 参数，而是先按文档类型设一个初始值，再用真实问题集做召回测试。测试时不要只看最终答案，要看正确依据是否被召回、是否排在前面、是否被 Prompt 选入上下文。只要召回材料不对，后面优化模型和 Prompt 都只能缓解，不能从根上解决问题。

 设计：给每个 Chunk 配一张身份证

Metadata 可以理解为每个 Chunk 的身份证。一个企业 RAG 系统里，Chunk 不应该只保存正文，还要保存来源、标题、章节、页码、文档类型、时间、部门、权限、版本等结构化字段。没有 Metadata，系统就很难做权限隔离、版本过滤、引用展示和问题排查。

images/rag\_metadata\_design\_redraw.png

Metadata 的价值主要体现在四个地方。第一是检索过滤，比如用户只想查“财务制度”或“2026 年版本”，系统可以先用元数据缩小范围，再做语义检索。第二是答案溯源，模型回答后可以标注依据来自哪份文档、哪一章、哪一页。第三是权限控制，不同用户只能检索自己有权限看的内容，避免把内部资料召回给无权限用户。第四是问题排查，当回答不准时，可以回看当时召回的是哪些 Chunk、来自哪个版本、是否被错误过滤或错误排序。

Metadata 设计不要只想着“字段越多越好”。字段太少，系统缺少过滤和追溯能力；字段太多但不稳定，入库维护成本会变高，还容易出现空字段、错字段和历史版本不一致。比较稳的做法是先确定必须字段，例如 source、title、section、page、category、updated\_at、permission、version，再根据业务需要扩展部门、项目、产品线、适用范围等字段。

# 七、常见问题与排查顺序

当 RAG 回答不准时，不要一上来就改 Prompt。更可靠的排查顺序，是沿着知识入库链路往前看。先看原文是否被正确解析，再看 Chunk 是否切断语义，再看 Metadata 是否缺失或错误，再看检索结果是否召回了正确片段，最后再看 Prompt 和模型输出。

如果召回片段内容本身错序、残缺或夹杂页眉页脚，问题通常在解析和清洗；如果召回的是同一篇文档但不是正确章节，可能是 Chunk 粒度或标题层级处理有问题；如果用户有权限却检索不到资料，或者无权限用户看到了内部内容，通常要查 Metadata 和过滤条件；如果召回结果正确但答案越界，才重点看 Prompt 约束和模型生成。

这也是为什么文档处理不能只交给一个批处理脚本后就不管。企业 RAG 需要保留入库日志、解析结果样例、Chunk 样例、Metadata 样例和召回评测集。只有这些证据完整，系统后续才有优化方向。
