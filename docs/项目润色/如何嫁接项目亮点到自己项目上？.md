# 如何嫁接项目亮点到自己项目上？

帮星球里的同学改简历，项目这一块是改动最多的地方。

几乎每一份都有同一个问题：做的东西不错，描述方式太平。

用 Cursor 搭了三周的 RAG 系统，简历上写的是"基于 LangChain 开发了文档问答功能"——技术选型的理由、调参过程、跑出来的效果数据，全部消失，剩下一行工具清单。

**项目本身没有问题，是"只写了做了什么、没写好在哪里"，让它看起来很普通。**

* * *

## 一、嫁接 ≠ 造假，但很多人没搞清楚这个区别

先把这件事说清楚，因为不少同学一听"嫁接别人的项目亮点"，第一反应是：这在简历上造假？

**造假是：把根本没做过的项目写进简历。**

**嫁接是：把你实际做过的项目，用更专业、更高维的框架重新描述。**

同样是做 RAG 系统，两种写法：

**写法 A（大多数人的写法）：**

> 基于 LangChain + ChromaDB 开发了企业文档问答系统，支持多格式文档上传与自然语言查询。

**写法 B（嫁接了表达框架之后）：**

> 面向企业内部知识管理场景，搭建基于 RAG 架构的多文档问答系统。使用 LangChain 管理文档分片与 Embedding 流程，向量存储采用 ChromaDB；针对长文档语义碎片化问题，对比测试了多种 chunk\_size 和 overlap 参数组合，最终将相关文档召回率从 63% 提升至 89%，平均响应时间控制在 2.1s 以内。

两个人做的东西差不多。写法 B 的人更容易过简历筛选。

* * *

## 二、为什么别人的项目看起来"更厉害"

认真看一批被面试官认可的简历，会发现一个规律：

**顶级的项目描述，结构是固定的。**

| 层级 | 内容 | 大多数人的问题 |
| --- | --- | --- |
| 问题背景 | 项目解决了什么现实问题？规模有多大？ | 直接跳过，上来就写技术 |
| 技术选型 | 用了什么？为什么这样选，不选别的？ | 只列工具，不解释判断 |
| 核心贡献 | 你个人具体做了哪个模块？ | 用"参与"糊弄，不够颗粒化 |
| 量化结果 | 提升了多少？优化了什么指标？ | 写"系统运行稳定"或直接空着 |

大多数人写的项目，第 1 层和第 4 层是空的。

结果就是：同样的项目，有人写出来让面试官想追问，有人写出来让面试官划走。

* * *

## 三、嫁接的具体操作：三步拆解法

### 第一步：找 3-5 份同方向的高质量项目描述

从哪里找？

-   **星球里已经拿到 offer 的同学分享的简历片段**——这是最直接的参考，方向匹配，且已被市场验证

-   **你目标单位的历年 offer 经验帖**——重点看项目描述是怎么写的，面试官追问了什么问题

-   **GitHub 上对应技术方向的热门项目 README**——学一流项目是怎么描述自己的价值和技术决策的

-   **身边已经入职目标单位的学长学姐**——直接问比什么都快

找参考的时候，**只看和你方向完全对口的**。你做的是 AI 应用方向，就只看 AI 应用的；你是数据分析，就看数据分析的。跨方向参考价值极低。

* * *

### 第二步：把对方的描述拆成"亮点单元"

不要整段抄，要拆解成可以单独迁移的模块。

一份好的项目描述，通常有以下几个可拆解的亮点单元：

**① 问题规模单元**

对方怎么写的：`处理超过 10 万条企业内部文档，支持 200+ 并发查询`

你的项目有没有类似的：你的数据集有多大？有没有并发要求或性能边界？哪怕是实验环境下的压测数据，也能写。

**② 技术选型理由单元**

对方怎么写的：`选用向量数据库替代全文检索，解决语义相近但字面不同的召回问题`

你的项目有没有：你当时为什么选这个技术栈？有没有对比过其他方案？你的理由是什么？

**③ 个人贡献颗粒度单元**

对方怎么写的：`独立完成 Reranker 模块设计与调优，以及 Prompt 工程迭代`

你的项目有没有：你在项目里负责的是哪个模块？是整体架构、数据流还是某个具体组件？

**④ 量化结果单元**

对方怎么写的：`召回率从 61% 提升至 88%，幻觉率降低约 35%，人工核查成本减少 60%`

你的项目有没有：有没有跑过评估实验？哪怕是自己设计的小规模测试，只要数据真实，就可以写。

* * *

### 第三步：把亮点单元对应回你的实际经历

这一步是核心，也是合法性的边界所在。

**原则只有一条：只嫁接你在面试里能说清楚的内容。**

面试官当场追问是一定会有的。如果你写了"通过 Reranking 策略将召回率提升 27%"，面试官问"你用了什么 Reranker？cross-encoder 还是 bi-encoder？"——你必须能答上来。答不上来，就不要写。

**三个常见的升维操作：**

**1\. 升维问题描述**

原版：`用 AI 做了一个简历分析工具`

升维：`针对校园招聘中候选人与岗位 JD 匹配效率低的痛点，构建基于 LLM 的语义匹配系统，将人工初筛 8 分钟/份缩短至 15 秒/份`

**2\. 加技术选型理由（最容易被忽略的一步）**

原版：`使用了 GPT-4o + LangChain`

加理由：`核心推理层使用 GPT-4o 保证输出质量，考虑调用成本，非核心分类任务切换为 Qwen-7B 本地推理，整体 API 成本降低约 65%`

**3\. 量化你实际测试过的数据**

原版：`系统效果良好，用户反馈正面`

量化：`在 80 份测试简历上评估，岗位匹配建议与招聘方人工判断的吻合率为 83%；冷启动（首次加载）时间 < 3s，连续对话响应延迟 < 1.5s`

注意：哪怕只是自己做的小规模测试，只要是真实跑出来的，就可以写进去。

## 四、Vibe Coding 时代，这件事为什么更重要了

现在用 Cursor、Claude、Copilot 辅助开发，两周能做出来一个像样的 AI 应用。

好消息是：有项目了。

坏消息是：大家都有了。

面试官一天看几十份简历，RAG 系统、AI 助手、智能客服——这些项目他已经看了几百份了。**项目本身不再是门槛，描述出"你在技术决策上动了脑子"才是。**

两种同学：

-   同学 A：用 Cursor 辅助开发，三周出了一个完整的 RAG 系统，但对 LangChain 的调用逻辑没有深究，Embedding 模型是默认的，chunk\_size 没调过。简历上写"基于 LangChain + OpenAI 开发了文档问答系统"，面试官追问技术细节，答不上来。

-   同学 B：同样用 Cursor 辅助，但在 AI 生成代码的过程中，把每一处关键的技术选型都搞清楚了——为什么用这个分片策略？Embedding 模型的选型逻辑是什么？有没有跑过对比实验？简历写出来有细节，面试回答得上来。

Vibe Coding 本身没有问题。**问题是有没有把 AI 帮你生成的东西真正搞懂，再写进简历。**

* * *

## 五、有一个背景你要清楚

背调能核实的，是你的就职经历和学历证书。

**项目描述本身，背调查不到。**

你在简历上写了"调优了 Embedding 策略"还是"用了默认配置"，没有任何外部机构会来核实——但面试官会当场问你，你是怎么调的？调优之前和之后的指标对比是多少？

所以限制不来自外部，来自你自己：**你能在面试里说清楚的内容边界，就是你简历上可以写的边界。**

写不清楚的，不写。能讲明白的，放开写，不要自我审查过度。

* * *

## 最后

Vibe Coding 把项目的技术门槛拉平了，同类项目满大街都是。

以前"用 AI 做了个 RAG 系统"还算亮点，现在这个描述面试官见过几百份，没有细节支撑的话，一秒划走。

别人的项目描述，本质上是一套**提炼框架**：把技术决策、选型理由、量化结果都逼出来，写进去。

回头用这套框架重新审视你自己的项目，能写的远比现在多。
